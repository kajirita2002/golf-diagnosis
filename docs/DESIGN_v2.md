### 2.1 1枚の流れ図

```
 ┌───────────────────────────────────────────────────────────────────────────┐
 │                         ホーム（今日の1点・状態・主ボタン）                    │
 └───────────────────────────────────────────────────────────────────────────┘
        │［撮る・入れる］
        ▼
 ① 撮る・入れる ─────────────▶ ② 課題が分かる ─────────▶ ③ 理想との差が見える
   動画（後ろから／正面から）      P1〜P7 をカタログで評価      自分のコマ＋ガイドの範囲の帯
   ・端末の中で P を取り出す       → ドミノ順で「まずここ」1つ    ＋課題の部位だけ範囲に入れた線
   TrackMan（スクショ・貼付・CSV） 球の課題（gist）は結果として   （参照動画・自分のベストとも）
        ▲                                                           │
        │                                                           ▼
 ⑦ 次の課題へ（ドミノの次）   ⑥ 直ったか              ⑤ 別の日に同じ置き方で撮る   ④ やること
        ▲                    10球テスト 8/10         （前回の P1 を薄く重ねて合わせる）  意識する1点・組み方
        │                    ＋ 球の判定（既存）              ▲                     合格の条件（8/10）
        └──── 合格 ◀──────────┘ ◀─────────────── 練習（①いつも通り…⑥10球テスト）◀──┘

```

- いまの実装にあるもの: ②〜④の球の側（`gist.py` の いま／課題／理想との差／やること）、⑥の球の判定（`coaching.py` の `STATE_TEXT`）、TrackMan の取り込み。
- 新しく足すもの: カタログ（§5）、P の取り出しと評価（§6）、範囲の帯と理想の線（§7）、10球テストと動きのプラン（§8）、輪として見える画面（§10）。

### 2.2 使う人と場面

| 場面 | 状況 | 画面に求めること |
|---|---|---|
| 練習場（TrackMan あり） | 片手に7番。スマホは三脚。電波は弱いことがある。サーバーは寝ている | 押すものは1つ（64px 以上・画面の下半分）。圏外でも止まらない |
| 練習場（TrackMan なし）／自宅の素振り | 動画だけ | 動画だけで1周できる。球の判定が無いことは断る |
| 帰りの電車・家 | 両手が空き、落ち着いて読める | 課題・理想との差・「なぜそう言える？」・前回との比較 |
| 次の練習の前（数日後） | 何を意識するか忘れている | 開いた瞬間に「今日の1点」と、撮る向き・組み方が出る |

- 使うのは本人1人（`auth.go` は Basic 認証の1つのパスワード）。**画面から「選手」を外す。** API の `players` は残し、最初の起動で1人を自動で作る。

### 2.3 1週間（典型。日の間隔は例）

| 日 | すること | アプリで起きること |
|---|---|---|
| 月（練習場） | 後ろから動画を1本（いつも通り5〜10球）＋TrackMan のスクショ | P コマを自動で取り出す → 自信の低いコマだけ確かめる → 評価 → 課題1つ |
| 月（帰り道） | 読む・決める | 課題・理想との差・意識する1点 →［このプランで始める］ |
| 水（自宅・任意） | 素振りを撮る | 課題の項目だけ見る（参考。判定には数えない） |
| 金（練習場） | 練習 | ①いつも通り（撮る＝前の測り直し）→ ドリル → 本番 → **⑥10球テスト（撮る）** |
| 金（練習後） | 取り込む | 「10球中◯回が範囲の中」と球の結果。前と後の同じ P を並べる |
| 翌週 | 繰り返す | 別の日にもう一度 8/10 →「効いた」、意識しない①で 8/10 →「定着した」→ ドミノの次の項目へ |

- **再確認を別の作業にしない。** 練習の①（いつも通り）が前の測り直しになり、⑥が10球テストになる。
- **1回の練習で扱うのは1項目**（ガイドは1〜2項目・ノート p119〜）。ドミノの次の項目は「次に見る」として1行だけ見せる。

### 2.4 1日（練習場の40分）

```
0:00 ホーム「今日の1点: 手とクラブを一緒に引く（P2）」［練習を始める］
0:01 三脚・撮り方ガイド（前回の P1 を薄く重ねて位置を合わせる）
0:03 ⓪準備5球 → ①いつも通り8球（撮る）→ ②ドリル → ③本番 → ④ドリル → ⑤本番
0:30 ⑥10球テスト（撮る。課題以外は気にしない。当たりも行方も問わない）
     撮っている間スマホは本体のカメラが使っている（この画面は裏）。打ち終えてアプリに戻ったら、
     **動画を見る前に**「できたと思った回数（0〜10）」と「やりすぎ気味／足りない気味／ちょうど」を1回だけ答える（任意）
0:37 TrackMan のスクショ → 取り込む
0:38 動画2本を選ぶ → 端末で処理（段で表示。時間は未確認）
0:40 「10球中◯回が範囲の中」と球の結果。読むのは帰り道でよい（閉じたら続きから）
```

## 3. 約束（この文書の全部に効く）

| # | 約束 | 中身 |
|---|---|---|
| R1 | **簡潔に、抽象化して** | 最初の面は言葉と絵だけ。角度・％・ボール何個・専門用語・ページ・英字は「なぜそう言える？」の中。画面の最初の層の文は全部 `gist.check_plain`（`config.PLAIN_FORBIDDEN`）を通す。「パス」「インパクト」「度」「％」「帯」も禁止語なので、P7 は「当たる瞬間」、ハンドパスは「手の通り道」、範囲の帯は「範囲」と書く。**`check_plain` は数字と英字も全部落とす**（`gist.py`）ので、当てる対象を決めておく: **所見の文**（カタログの `title` / `look_at` / `ok_text` / `faults[].label`・gist の4つ・判定の文・次の手）には素の `check_plain` を当てる。**構造のラベル**（P の番号チップ「P2」・10球テストの「10回中8回」・日付・件数の見出し・料金のボタン・所要時間）は数字を許すが、許す形を `check_plain_label(text, kinds=("p","count","date","cost","duration"))` の正規表現で固定し、それ以外の数字・英字は落とす。所見の文の中に「P2」を書かない（P はラベルとして横に置く） |
| R2 | **1回に1点** | 課題は1つ。「次に見る」は1行だけ。ガイドの「1回の練習で1〜2項目」 |
| R3 | **動きと球筋を言い切らない** | ガイド自身が「動作は起こりやすさに効くだけで確定ではない」（p133〜）。つながりは事前の表（§9）に載った組み合わせだけ、「〜の可能性があります（まだ確かめていません）」まで |
| R4 | **偽の確信を出さない** | 確率を出さない。判定はガイドと同じ「範囲の中／範囲の外」に「判断できない」を足した3つだけ。独自の中間の段（ずれ小など）を作らない。範囲の端の誤差の内（境目）は「判断できない（境目）」 |
| R5 | **分からないことは理由つきで分からないと言う** | 測れない項目も消さない。「この撮り方では判断できない」＋何があれば見られるか（正面で撮る・240fps・圧力を測る板など） |
| R6 | **Claude に数字を作らせない** | Claude の出力は選択肢（範囲の内／外・寄りの向き・判断できない）だけ。数字が入った答えは捨てる。角度・位置はサーバーが姿勢の点とタップから計算する |
| R7 | **ガイドを写さない** | カタログ・ドリル集・画面の文に、ガイドの文章と図を入れない。項目ごとに自分の言葉の要約・数値の範囲・ページだけ |
| R8 | **権利** | プロの写真・他人の動画・AI の生成画像をリポジトリにもアプリにも入れない。理想の線は本人の骨格から計算して描く。参照動画は本人の端末の中だけ |
| R9 | **動画は端末で処理** | サーバーに送るのは数値（姿勢の時系列・タップ）と、評価のときだけコマの JPEG（保存しない）。左打ちは反転して右打ちの座標で見る。文の「左右」は `{lead}` / `{trail}` で差し込む |
| R10 | **判定の文は定型文** | カタログの文と `claims.py` の定型文だけで組む。Claude の文は「なぜ？」の中で「AI が見た様子」として引くだけ |
| R11 | **多重比較を防ぐ** | 項目が多いぶん、偶然の外れが必ず出る。①境目は判断できないにする ②項目の状態は複数スイングの多数で決める ③TrackMan と結ぶのは事前の表だけ |
| R12 | **同じ条件で比べる** | 向き・カタログの版・置き方・番手がそろわない2つは並べない（または位置の項目を外し、理由を出す） |

### 4.1 画面に出す名詞は5つ


- **タブは4つ、どれも場所**（HIG: タブバーは場所の行き来に使う）。「撮る・取り込む」は操作なのでタブにしない。ホームの主ボタンと、記録の画面の主ボタンに置く。
- **ルーティングはハッシュ**: `#/home`・`#/record/{date}`・`#/session/{id}`・`#/session/{id}/check`・`#/session/{id}/check/{itemId}`・`…/ideal`・`#/practice`・`#/progress`・`#/settings`。いまは状態がメモリの `S` だけにあり、再読み込みすると最初の画面に戻る。

### 4.3 見せ方の階層（全部の画面で同じ形）

| 層 | 出すもの | 例 |
|---|---|---|
| 1 最初の面 | 言葉と絵。状態の印（形・色・文字） | 「クラブが体の内側に引かれています」△ 範囲の外 |
| 2 「なぜそう言える？」（下から出るシート） | どのコマか・根拠の札・何本から言ったか・先に直す理由・ガイドの節とページ・球とのつながり（可能性として） | 「基準: PGA スイングガイド p38（アイアン・後ろから）」 |
| 3 「数字を見る」（シートの中で開く） | 範囲・測った値・誤差・代わりの点・撮り方の検査の結果 | 「範囲: 手のまわりボール1個以内／あなた: 約2個 内側（8本中6本）・誤差 ±0.4個」 |

### 4.4 課題を1つ選ぶ規則（`checkpoints/judge.py` の `pick_focus`）

1. **動画のチェックがある日**: 「範囲の外」の項目のうち、候補にできるものだけを並べる。
   - 候補にできる: 根拠が「測れた」で**3本以上のスイングの多数**が範囲の外、または「見た目」で**2本以上が一致**して範囲の外。
   - 候補にしない: 判断できない（境目・食い違い・定義を確かめ中を含む）・参考の項目・1本だけの見立て・撮った向きと違う向きの項目。
2. **並べ方（点数を使わない）**
   1. `domino_rank` の小さいものが先（前半ほど後ろ全体に効く。P1-2 → P2-3 → P3-4 → P4-5 → P5-6 → P6-7。ノート p158〜）。セットアップ（P1）は同じ段の先頭。
   2. 同じ段では「手の通り道」（`group: path`）を、ヘッドの位置・シャフト角より先（ノート p28〜「まずハンドパス、次にシャフト角」）。
   3. 同じ段では「測れた」を「見た目」より先。
   4. それでも並んだら、範囲の外だった回数が多いもの。
3. 出すのは1つ。**「次に見る」を1つだけ**下に薄く添える。
4. **動画が無い日**: 既存の `gist.focus`（球の課題）を課題にする。
5. **両方がある日**: 課題は動きの側。球は「結果」として同じ画面に並べる。事前の表（§9）に載った組み合わせのときだけ「球の課題とつながる候補」の印を付ける。**印は順番を変えない**（順番はガイド、TrackMan は答え合わせ）。
6. **飛距離の項目**（§5.3 F と `tags: distance`）も、ほかの項目と同じ規則（1〜2）で候補になる（パワーの項目にも `domino_rank` がある。飛距離だけ後回しにする根拠はガイドに無い）。本人が設定か診断で「飛距離を優先」を選んだときだけ、`distance` を持つ候補を先頭に寄せる（その中はドミノ順）。`×`・参考の項目は、どの設定でも課題にならない。
- 選んだ理由は `rationale` に残し、「なぜそう言える？」の1行目に出す（「スイングの前半ほど、後ろの動き全部に響くため先にここ（ガイドの考え方）」）。見えているずれの原因はひとつ前のポジションにあることが多い（ノート p70）ので、「次に見る」の説明にも使う。

- ガイドは比を**1つの値**で書いていて範囲が無い。範囲を作ると、ガイドに無い基準を作ることになる。だから合否を出さない。
- 誤差: 時刻それぞれに ±1コマを足して比の幅を出す（60fps だとダウン約16コマで比が約 ±0.3 動く。3:1 と 2.8:1 は見分けられない）。
- 言葉にするのは、誤差の幅がガイドの値から人が決めた余白（初期値 0.3・要較正）を超えて離れたときだけ。言葉は「上げに比べて下ろしが短め／長め」の中立の言い方にする（比からは、上げと下ろしのどちらのせいかは分からない）。「ガイドの目安の近く」と言うのは、幅が丸ごと目安±余白の中に収まるときだけで、どちらでもなければ「どちらとも言い切れない」。幅は ±1コマを、実際に取ったコマの間隔（間引いて取ったなら間引いた間隔）で作る。30fps（`CP_MIN_FPS_CLUB` 未満）は判断できない（§6.2）。値が出たのが1本だけなら「一本だけの見立て」を添える（R11）。
- 始動の定義（手がアドレスから 0.08L 離れ 100ms 離れ続けた最初のコマ）は**こちらで決めたもの**で、ガイドの測り方は未確認。「なぜ？」に書く。
- 240fps なら誤差が小さくなり言葉にできる幅が広がる。

### 6.2 撮り方（ガイドのカメラアングル・ノート p158〜183）

| | 後ろから | 正面から |
|---|---|---|
| 縦の中心線 | グリップエンドと手の中心のあいだ（ボールと体の真ん中に合わせるのは不可） | スタンスの中央 |
| 横の中心線 | 腰骨の高さ | 腰骨の高さ |
| レンズ | ゴルファーの真後ろ。左右に角度を付けない | 腹の高さ。煽り・見下ろしにしない |
| 共通 | 三脚・横向き・レンズ1倍（0.5倍は端が歪む）・頭の上からヘッドまで全部入れる・ボールの横に目標線と平行な棒 | 同左 |

- **合わせる画面（任意）**: `getUserMedia` のプレビューにガイドの格子と**前回の P1 の骨格を薄く**重ねる。録画は本体のカメラでする（ブラウザの録画は高い fps を出せない）。`getUserMedia` が使えないときは、撮った1本目で ○／× を出す。**`getUserMedia` のプレビューと本体のカメラの写る範囲は同じとは限らない**（レンズ・切り抜き・縦横比が違うことがある。未確認）ので、プレビューで合わせても、撮った1本目の P1 で必ず置き方の自動チェックをもう一度かける（プレビューは目安、判定は撮った動画で）。
- **置き方の自動チェック**（P1 のコマで）: 腰の点の高さと画面の横の中心線の差、手首と縦の中心線の位置、足元の棒の消失点（§9.2 のまま）。外れたら直す向き（「カメラをもう少し右へ」）を返す。外れたまま進むと、その向きの角度の項目は全部「判断できない（カメラの置き方）」。

- **試し撮り**: 初回は1本目でチェックが通るまで先へ進めない（NN/g #5）。

### 6.3 コマの取り出し（ブラウザ・`web/video.js`）

1. **選ぶ**: `<input type=file accept="video/*">`。向きと番手は前回の値が入った状態。TrackMan の球と対応づけられれば番手はそこから取る。
2. **デコード**: 本命は WebCodecs の `VideoDecoder`＋同梱の mp4box.js。使えないときは `<video>`＋`requestVideoFrameCallback`。1コマずつシークする方法は使わない。
3. **粗い走査**（短辺 160px）でスイングの区間を出す。素振り・ワッグルを除く。
4. **姿勢推定**（区間の前後・短辺 360〜480px。いまは短辺 360px。細かく取る区間の頭は P1 の 0.5秒前まで。一回に送るコマが 6000 を超えるときはスイングの組に分けて送り、点は小数4桁に丸める）: MediaPipe Pose Landmarker lite（人のマスクつき）。33点と visibility を時系列で持つ。**全スイングで端末の中で回す（無料）。**
5. **ボールを2点タップ**（直径の両端。最初のスイングの P1 で1回）。P7 の挟み込みと、ボール1個の物差しの両方に使う。
6. **P の検出**: 時系列を `POST /v1/video/checkpoints` に送る（数値だけ・保存しない）。規則はサーバーの `video.py`（`video/0.2`）に1か所で持ち、pytest で固定する。
7. **切り出し**: 各コマを全解像度でデコードし直し、人の外枠を中心に上下左右にクラブの長さぶんの余白を取って長辺 1024px の JPEG にする（**縦横比は元のまま。3:4 に切らない**）。IndexedDB に置く。長辺 360px のサムネイルと、姿勢の点・タップはサーバーにも保存する。
8. **確かめる**: R2（§10）。**自動で決めたコマはそのまま使い、確かめるのは自信の低いコマ・課題の P・タップの要る点だけ。**

- 同梱: MediaPipe の WASM とモデル、mp4box.js は `web/vendor/` に版入りのファイル名で置く。`/vendor/` にだけ `Cache-Control: immutable` を付けるハンドラを Go に足す。
- `sw.js`: `video.js` は `SHELL` に入れる（圏外でもコマ出しと10球テストの数えができるように）。`vendor` は入れない（10〜20MB の見込み・未確認）。
- 処理中は Wake Lock を取り、段で進み具合を出す（読み込み → スイングを探す → 体の点を取る → P を選ぶ → 測る）。％は出さない。［止める］を置き、閉じたら「続きから処理する」。処理時間と端末は `capture_json.perf` に残し、次からその端末の実測で目安を出す。
- 最初の保存の前に `navigator.storage.persist()` を頼む。拒まれても比較はサーバーのサムネイルと点でできる（iOS Safari はホーム画面に追加していないサイトの保存領域を7日使わないと消すことがある）。

### 6.4 P の定義と検出（`video/0.2`・初期値・要較正）

記号: H＝手の中心の代わり（両手首の中点）、Sₗ＝`{lead}` 側の肩、Hip＝見えている側の腰、L＝胴の長さ、画面の y は下が正。

| P | ガイドの定義（要約） | 検出の規則 | 必須 |
|---|---|---|---|
| P1 | 打つ前の構え | 始動 t₀（H がアドレスから 0.08L 離れ 100ms 離れ続けた最初のコマ）の直前の静止区間の最後 | ○ |
| P2 | バックでシャフトが地面と平行 | t₀ のあと H.y が Hip.y に達した最初のコマ。**正面でクラブをタップしたら、シャフトが水平に一番近いコマへ寄せ直す**（前後3コマ）。タップが無ければ「P2 の目安」 | ○ |
| P3 | バックで `{lead}` 腕が地面と平行 | P2 のあと、Sₗ→`{lead}` 手首の線が画面で水平 ±10° に最初に入ったコマ（後ろからは腕が胴に隠れると「目安」） | ○ |
| P4 | ヘッドが下り始める直前 | P3 のあと、なめらかにした H.y が最小のコマ。タップがあればヘッドの向きが変わるコマへ寄せる | ○ |
| P5 | ダウンで `{lead}` 腕が地面と平行 | P4 のあと H.y が Sₗ.y を下向きに通った最初のコマ | ○ |
| P6 | ダウンでシャフトが地面と平行 | P5 のあと H.y が Hip.y に達した最初のコマ（正面ではタップで寄せ直す） | ○ |
| P7 | 当たる瞬間 | ボールの ROI で挟む（既存 §9.4） | ○ |
| P5.5 / P6.5 | 中間（エラーの基準で使う） | 両端の時刻の中点のコマ（「目安」） | 任意 |
| P8 | フォローでシャフトが地面と平行 | P7 のあと H.y が Hip.y に達した最初のコマ | 任意 |
| P9 | フォローで `{trail}` 腕が地面と平行 | P8 のあと `{trail}` 肩→手首の線が水平に入った最初のコマ | 任意 |
| P10 | フィニッシュ | H の速さが 0.3L/s 未満の状態が 0.3秒続いた最初のコマ | 任意 |

- 後ろからの P2・P6 はシャフトがカメラを向いて短く写るので、水平かどうかは画像から測れない。**代わりの規則で決めたときは「P2 の目安」と表示**する（`swing_frames.method` / `status` に残し、R2 の帯・C の帯・C-1 に「目安」と出す）。
- 正面の寄せ直し（P2・P6）で `ok` にするのは、前後3コマの中にタップが2つ以上あり、一番水平に近いものが 15° 以内で、その前と後のコマにもタップがあるときだけ。タップ1つでは目安のまま（段2b のレビュー）。**画面はまだ前後のコマのタップを集めない**（§6.5 のタップは3種類だけ）ので、製品の流れでは正面の P2・P6 も目安のまま出る。集めるかは段5で決める。
- 後ろからの P3 は、腕がカメラの方を向いて短く写るので、画面の上の腕の傾きでは水平かどうかを決められない。いまは後ろからは常に代わりの規則（手が {lead} 肩の高さ）で決め、「目安」とする（表の「隠れたときだけ」より控えめな側）。
- 素振り（ボールが動かない）として外すのは、そのスイングの構えで、丸の中が最初にタップしたボールの絵と似ているとき（`ball_seen`）だけ。似ていなければ（新しいボールが丸から横に置かれた）外さない。全部が素振りに見えたときも外さずに返す（行き止まりにしない）。R2 に［外さずに使う］を置く。
- 順番の検査: P1＜P2＜…＜P7 に反した P は「見つからない」。バック（t₀→P4）が 0.6〜1.5秒、ダウン（P4→P7）が 0.2〜0.5秒を外れたら警告。
- 返す形: `{p, t, frame, source: auto|manual, method: rule|ball_roi|club_tap|midpoint, status: ok|estimated|failed, reason, dt_ms}` と t₀。
- **P1〜P7 は必ず7枠を並べる。** 見つからない P は R2 で本人に選んでもらうか、「このPは写っていない」を押す。押した P を使う項目は「判断できない（コマが無い）」になり、評価は止めない（行き止まりにしない）。

### 6.5 クラブ（シャフト・ヘッド・グリップエンド）の取り方

| 取り方 | 採否 | 理由 |
|---|---|---|
| **本人の2点タップ**（グリップエンドとヘッドの中心） | **本命** | ガイドの基準の多くは線の角度と位置なので座標が要る。Claude に座標を作らせない約束を守れる |
| Claude が選択肢で答える（「シャフトは `{trail}` 二の腕の中央より上か下か」「ヘッドは手元より内／重なる／外」） | 採る（位置の関係で決まる基準と、タップが無いときの見た目） | 範囲と比べる数値は出さない |
| 画像処理の下書き（手元の縁から直線を当てて提案）＋本人の確認 | 段5 以降の任意 | 精度未確認。本人が「合っている」を押してから使う |
| Claude に角度・座標を読ませる | **採らない** | 較正されていない数字を「測った」に見せてしまう |

- **タップを求めるのは3つだけ**（全部の P・全部のスイングには求めない）:
  1. 最初の記録の代表スイングの **P2 のヘッド**（ドミノの起点。1回だけ）
  2. **課題の項目**が要る P（10球テストでは10スイングのその P だけ）
  3. 本人が任意で押す「クラブの位置を付ける（約1分）」＝代表スイングの P1〜P7（付けると見られる項目の数「+18項目」を添える）
- それ以外のクラブの項目は、代表スイングで Claude の「見た目」に回す。タップも見た目も無ければ「判断できない（タップすると測れます）」。
- 60fps で P6〜P7 のヘッドがブレて見えないときはタップを求めず「判断できない」。
- **タップの UI**: コマはピンチで拡大できる（拡大しても押した座標はコマの画素に戻して保存）。押した所の上に2倍の拡大鏡を指から離して出す（利き手の設定で左右を入れ替え、指で隠れない側に出す）。置いた点は上下左右に**コマの画素で1つずつ**動かすボタン（44px。長押しで連続）で直せる（WCAG 2.5.7）。いま置いているのがどの点か（「グリップエンド」「クラブの先」）を拡大鏡の上に字で出し、点は形でも分ける（グリップエンド＝四角、先＝丸）。スクリーンリーダーでは点を置けないので、［このコマは飛ばす］がいつでも届く位置にあり、飛ばした項目は「判断できない（点が無い）」になる。前のコマの点を次のコマの初期位置に置く。［やり直す］［決定］［このコマは飛ばす］。
- タップと Claude の見た目の向きが逆なら**タップを採り**、食い違いを「なぜ？」に残す（§6.6 の表では、測った値と見た目が逆のときは判断できないにする。タップは本人の指示なので、タップのときだけ例外としてタップを採る）。
- タップは `swing_frames.taps_json` に保存する。同じコマを2回押したときの差を誤差の予算に入れる。

### 6.6 判定（`checkpoints/judge.py`・LLM を使わない・`judge/1.0`）

1. **測る**（`measure.how` が vision 以外）: 使う点の visibility が 0.6 未満・カメラの置き方のチェックに落ちた・タップが無い・物差しが食い違う、のどれかなら無効。有効なら値と誤差から「範囲の中／範囲の外／境目」。
2. **見る**（`vision` を持つ）: 選んだ選択肢を状態に写す。`not_visible`・「判断できない」は判断できない。
3. **合わせる**

   | 測った結果 | 見た目 | 状態 | 札 |
   |---|---|---|---|
   | 中／外 | 同じ向き | 測った状態 | 測れた（＋見た目も一致） |
   | 中／外 | 無し・判断できない | 測った状態 | 測れた |
   | 中／外（姿勢） | 逆の向き | 判断できない（食い違い。両方を「なぜ？」に） | — |
   | 中／外（タップ） | 逆の向き | タップの状態 | 測れた（あなたが示した点から）・食い違いを記録 |
   | 境目・無効 | 答えあり | 見た目の状態 | 見た目 |
   | 境目・無効 | 無し | 判断できない | — |

4. **何スイングもあるとき**: スイングごとに状態を出し、項目の状態は判定できたスイングの**多数**で決める（姿勢・タップは全スイング、見た目は Claude に出したスイングだけ）。1本しか判定できないときは「1本だけの見立て」と書き、課題の候補にしない（R11）。まとめは「8本中6本が範囲の外」と**回数**で書く。
5. **根拠の形**: `{state, fault, basis: measured|measured_approx|visual|conflict|none, reason, n_judged, n_out, frames, value:{q, v, err, unit, lo, hi}, proxy, vision:{option, visual}, pages, catalog_version}`。

### 6.7 Claude に聞くこと

**渡すもの・渡さないもの**

| 渡す | 渡さない |
|---|---|
| そのスイングの P1〜P7（あれば P5.5・P6.5・P8〜P10）の JPEG（長辺 1024px）と拡大2枚、向き、fps の実測、各 P の定義の一文 | TrackMan の数字・症状・課題・`l1_links`・姿勢の値・タップ・過去の評価・**ガイドの範囲の数値**・日付 |
| その向き・その番手で `vision` を持つ項目の質問と選択肢のラベル | カタログの `title` と良い側の説明（誘導になる） |

- 画像には「P1」などとだけ焼き込む。選択肢の並びは項目ごとに毎回ランダムにし、サーバーが元に戻す。
- 呼び方は `screenshot.py` と同じ（`MODEL`・構造化出力・`effort: "medium"`・`stop_reason` の確認・応答の `model` を記録）。
- **既定で出すのは2スイング**（代表＝①いつも通りの真ん中、ともう1本）。見た目の項目を「2本以上で一致」で課題にできるようにするため。1回の依頼にまとめる。
- 10球テストでは、課題の項目が見た目のものなら10コマを1回の依頼でまとめて聞く。測れる項目は Claude を呼ばない。
- **参照動画のコマは Claude に送らない**（他人の画像を外に出すことになる）。

**出力**（スキーマはカタログから毎回作る）

```json
{"frames": [{"swing": 1, "p": "P3", "is_phase": "yes|no|unsure", "note": "…"}],
 "answers": [{"swing": 1, "item": "err.early_rot.p6", "option": "o2",
              "visibility": "clear|partial|not_visible", "visual": "…"}],
 "extra": ["…"]}
```

**検証**（落ちたら1回だけ指摘をつけて頼み直す。それでも落ちた項目は出さない）
- スキーマに合う・渡した項目と選択肢だけ・全項目に1回ずつ。
- `visual` / `note` に数字・度・`PLAIN_FORBIDDEN` の語・症状の語が無い（60字まで）。
- `is_phase: no` のコマを使う答えを捨て、「P3 を選び直してください」と出す。
- 画面に「検証を通らなかったので出していない項目（2件）」と出す。`extra` は表示だけで判定に使わない。
- 60fps の P6・P7 のクラブの細部と、ブレた拡大は「判断できない」を既定にするよう指示する。

**正しさの測り方**: 測れる項目と見た目の項目が重なるもの（脚の見え方と姿勢の visibility など）は測った値を正解として一致率を測る。見た目だけの項目は、同じ入力で2回・左右反転で聞いたときの一致率だけを測り、**これは正しさではない**と書く。`PROMPT_VERSION = "checkpoints_q/1.0"` ごとに `llm_jobs` で集計する。

**費用（未測定の見積もり）**: 1スイングあたり画像9〜14枚で入力約 10〜16k トークン、見た目の項目は1つの向きで20〜25問、出力約 2〜4k トークン。単価は `screenshot.py` の $4 / $20 per 100万トークンで **1スイング約 $0.08〜0.14、既定の2スイングで約 $0.16〜0.28**。評価は本人が押したときだけ（料金を出して押させる）。ジョブ（`llm_jobs`・202 を返して取りに行く）・キャッシュ（鍵は JPEG の sha256・カタログの版・`PROMPT_VERSION`・model）・上限（`LLM_DAILY_LIMIT_VIDEO`）は既存 §5.8 のまま。画像は Go が `MaxBytesReader` で受け（1枚 1.5MB・32枚まで）、Claude に渡したら捨てる。

### 7.2 ①の作り方（帯が本体、線は補助。`web/checkpoints.js`＋`POST /v1/checkpoints/ideal`）

- **全身の理想の骨格は作らない。** ガイドは部位ごとの範囲を決めているだけで、全身の1つの姿勢は決めていない。全部を同時に満たす全身を 2D で作ると、成り立たない形や範囲の中の1点を「正解」として描いてしまう。
- **帯（本体）**: 課題の項目の範囲を本人の P1 の点とタップ（つま先・ボール・グリップエンド）から描く。例: P2 後ろの手の中心は「つま先の縦線〜ボールまでの距離の1/4外の縦線」の帯、P3 のシャフト角は「垂直から30〜40°」の扇。ボール1個の物差しで描く。**数字は描かない。**
- **線（補助）**: 本人のその P の骨格のうち、**範囲の外の部位だけ**を、関節の長さを保って回し、範囲の一番近い端の少し内側まで動かす（最小の変化。範囲の中央へは寄せない）。腕なら肩を中心に肘・手首を回し、シャフトなら手元を中心に回し、手の位置なら手首を平行に動かす。本人の元の部分は白の実線、動かした部分は `--ov-gap` の**破線（6 4）で太さ1.5倍**にし、今の線から新しい線へ短い矢印を引く（**色だけで区別しない**＝WCAG 1.4.1。線の種類と太さと矢印でも分かる）。図の上に1行の凡例（線の見本つき「白＝いまのあなた／破線＝範囲に入れた目安」）を必ず出す。
- 描くのは**「まずここ」の1項目だけ**。範囲の中・境目・判断できない・基準を確かめ中の項目は描かない。見た目の項目は帯を描かず、見る場所を丸で囲む。
- 画面の注記（常に出す）: 「あなたの形のうち、色の部分だけをガイドの範囲に入れた目安です。この形で良い球になるかは、まだ確かめていません」。
- **代わりの文**: 重ねた図には、層1の所見の文と同じ定型文を `aria-label`（`<svg>` なら `<title>`／`<desc>`）に入れる（「クラブの先が手より内側。範囲は手と重なる位置」）。画像だけで差を伝えない（WCAG 1.1.1）。
- テスト: 動かしたあとの値を判定し直すと範囲の中になる。範囲の外の部位以外の点は動かない。関節の長さが変わらない。

### 7.3 見せ方

- 切り替えは3つ（セグメント）: **範囲**（既定。範囲の帯を重ねる。「帯」は `PLAIN_FORBIDDEN` の語なので画面の言葉にしない）／**並べる**（②か③と同じ P をそろえる）／**動かして比べる**（P の区切りで区間ごとに時間を伸び縮みさせて同時に流す・0.25倍）。
- 縦持ちの「並べる」は**上下**（左右だと1枚 144px で見えない）。横向きか広い画面だけ左右。［自分］［参照］［交互］で1枚に切り替える形も置く。
- 重ねるときは P1 の足元の中点・ボール・肩・腰で位置を、胴の長さ L で縮尺を合わせる。回転は小さく制限する。左右の利き手が違う参照は描くときだけ反転する。
- P の移動は3通り: P1〜P7 のチップ（44px）・前後のボタン・左右のスワイプ（スワイプは代わりの操作で、ボタンで全部できる）。透け具合は 0／50／100% の3段のボタン。
- `prefers-reduced-motion` のときは自動で流さず、［交互］も自動で切り替えない。
- ③を初めて選ぶとき1回だけ: 「この動画は端末の中だけで使います。送信しません。他の人の動画は、使ってよいものだけを選んでください」。端末に何本あるかの表示と、消すボタンを設定に置く。

### 8.2 10球テスト（ガイド p158〜183）

- **項目は1つ**（プランを作った時点で固定。あとから足せない＝良く出た項目を選べてしまうため）。その項目に要る向きとコマだけを取り出す（P2 の項目なら P1 と P2 だけ）。
- **撮り方**: 基準の日と同じ向き・同じ置き方（前回の P1 を薄く重ねて合わせる）。課題以外は意識しない・当たり方も行方も問わない、と撮る前に1行出す。
- **自己評価**（任意）: **10球を打ち終えてから、動画を見る前に1回だけ**「できたと思った回数（0〜10 のステッパー）」と「やりすぎ気味／足りない気味／ちょうど」を答える。1本ずつ押す形にしない ―― 撮影中はスマホの本体のカメラが前に出ていて、この画面は押せない（三脚の上のスマホを1球ごとに触ると置き方もずれる）。2台目の端末があるときだけ、1本ずつ押す形を設定で選べる。
- **数え方**: 測れる項目だけで数える（Claude を呼ばない・無料）。クラブの項目は10スイング × そのコマの2点タップ（約5分の見込み・未確認）。見た目でしか判断できない項目なら10コマを1回の依頼でまとめて聞き、「見た目で数えました」と札を付ける。
- **判定**
  - **合格**: 判定できた中で範囲の中が 8 以上、かつ判定できたスイングが 8 以上。
  - **まだ**: 範囲の中が 7 以下。
  - **判定できない**: 判定できたスイングが8に満たない（「撮り直し」と足りない数を書く）。**合格に要る数を黙って下げない。**
  - 表示は分母を正直に: 「9回中7回が範囲の中（判定できなかった1回を除く）」。
- **次の手（ガイドの調整の仕方）**: 逆側に外れた回が多い → 「加えた感覚が多すぎます。次は少し減らします」。同じ側のまま → 「感覚が足りません。もっと大胆に」。次の撮影の前に、どれくらい変えるかを1つ選ばせる。
- 自己評価との比べ（「できたと思ったのは8回、範囲の中は6回」）も添える（感覚と実際のずれに気づくため。1本ずつの対応は、1本ずつ押したときだけ）。
- 「8/10 はガイドの練習の合格ラインで、確率ではありません」を「なぜ？」に書く。
- ガイドの別の「スキルテスト（10球で7/10）」はターゲットを狙う練習の合格ラインで、動きの項目の10球テストとは別物。混ぜない（球の側で使うかは段5で検討）。
- **フィードバックループ**: 撮影 → 分析 → 修正 → 再撮影を数え、2〜4回やっても合格しないときは「2〜4回の撮り直しで変わらないことがあります。ドリルを替えるか、コーチに見てもらう段です」（`switch_drill` / `video_or_coach` の次の手）。約束はしない。
- 合格したら、ドミノの次の項目を「まずここ」に上げる候補として出す。

### 8.3 動きのプラン（既存のプランを広げる）

- `plans` に `kind: ball | motion` を足す。`motion` のプランは KPI がカタログの項目 id、合格の条件が10球テスト。
- 状態の**見出し**は `STATE_TEXT` の見出し（「効いたかも」「効いた」…）を使い回す。**2つ目の文は使い回さない** ―― 今の文は球の話（「判定に要る球が足りませんでした」「道具があるとできています」）で、動きのプランに出すと嘘になる。`coaching.STATE_TEXT_MOTION`（同じ鍵・2つ目の文だけ。例 `insufficient`＝「判定できたスイングが八回に届きませんでした」、`not_transferred`＝「意識するとできています。意識しない最初の撮影に移す段です」）を足し、`check_plain` のテストに入れる（数字を使わない）。`stuck` と `pending` は動きのプランでは使わない。判定の規則は `coaching.py` に足す:

  | 起きたこと | 状態 |
  |---|---|
  | その日の⑥で 8/10 | 効いたかも（`maybe`） |
  | 別の日の⑥でもう一度 8/10 | 効いた（`worked`） |
  | 意識しない①（いつも通り）の撮影で 8/10 | 定着した（`settled`） |
  | ⑥は合格・①は外が多い、が2回 | 移せていない（`not_transferred`） |
  | 10球テストが**別の日に4回**続けて合格しない（ガイドの「2〜4回」の上の端。2回目・3回目の不合格では「感覚の量を変える」の次の手だけ出す） | 効かなかった（`failed`）→ ドリルを替える（`switch_drill`）か、コーチ（`video_or_coach`） |
  | 判定できたスイングが8に満たない | 足りない（`insufficient`） |
  | 見張り（振りの速さ・キャリー）が続けて落ちた | 止める（`stop`）＝既存の `config.DEFAULT_GUARDRAILS` を動きのプランにも付ける |

- 1回の練習の組み方は既存の型（⓪準備 → ①いつも通り → ドリル／本番の交互 → ⑥10球テスト）。①と⑥で「🎥 撮る」を示す。
- **今の表との合わせ方**（`store.go` の制約）: `plans` は `drill_id` / `catalog_version` / `club` / `target_metric` / `goal` が NOT NULL、`plan_runs.experiment_id` も NOT NULL で `experiments` を指す。動きのプランは、`target_metric` を `cp:<項目id>`・`goal` を `in_range`・`drill_id` はチェックポイント版のドリル・`catalog_version` はドリル集の版で入れ、**練習1回ごとに実験の行も作る**（`hypothesis` は意識する1点、`target_metric` も `cp:<項目id>`。TrackMan の球が無い日はブロック0個の実験）。Python の `evaluate` は `cp:` の指標を知らないので、Go が `cp:` のときは `evaluate` を呼ばず `focus_tests` から評価を作る。動いているプランは選手ごとに1つ（`plans_one_active`）なので、球のプランが動いているときに動きのプランを始めるのは既存の `?replace=1`（前を `switched`）で、シートの中で「いまのプランを置き換えます」と断る。

### 8.4 TrackMan の再確認（判定を2つ作らない）

- 項目がプランの KPI・番手と同じなら、**`plan_runs.evaluation_json` と `STATE_TEXT` の言葉をそのまま出す**。
- プランの KPI 以外（見張り・飛距離の行）だけを新しく計算する。`compare._diff` は変えず、`checkup.verdict(diff, goal, mmd)` を足す:

  | 言葉 | 条件（初期値） |
  |---|---|
  | 良くなった | 区間が0をまたがず、良い向きで、MMD 以上（`_diff` の `changed`） |
  | 悪くなった | 同じ条件で悪い向き |
  | 変わらない | 両日とも5球以上、区間が ±MMD の中に収まる |
  | 判断できない | それ以外。理由と球数を書く |

- **`same` を「変わらない」と読まない。** 球数の見積もりは言葉ごとに出す（区間の半幅 h = 1.96×SD×√(2/n)）: 「良くなった」を見分けるには h ≤ 2×MMD、「変わらない」と言うには h ≤ MMD。9番の打点（SD 11.1mm・MMD 4mm）で約15球と約59球、フェース（SD 7.8°・MMD 1°）で約117球と約470球 → フェースは「1日では判断できない」を既定にし、帯に入った球の件数を並べるだけ。画面では「この日の球数では『変わらない』とまでは言えません。変化があれば分かる数は打てています」のように言える範囲を書く。
- 基準の日が診断した日（いちばん悪い日）なら、平均への回帰の注記を添える（既存 §2.2）。
- 振りの強さが違う日（クラブスピードの差が MMD の2倍以上）は、キャリーを「判断できない（振りの強さが違う）」にする。
- 動画は A のブロック（いつも通り）で撮るのを勧める。B は意識して打っているので形の比較に混ぜない。

### 8.5 別の日と比べる

- **同じ向き・同じカタログの版・同じ置き方**（§6.2 の確かめに通ったもの）どうしで並べる。違えば位置の項目を外し理由を出す。版が違えば「基準が新しくなったので比べません」。新しい版で評価し直すのは Claude をもう一度呼ぶので、料金を出してから押させる（基準の日の JPEG が端末に残っているとき。1スイングずつ・日付を伏せて出す。両日を1回の要求に混ぜない）。
- 言葉: 「範囲の外（8本中6本）→ 範囲の中（10回中8回）」。10球テストの合格・不合格以外の確率や「直った」は言わない。
- 比べ方は帯を重ねたスライダー（既定）。前と後の同じ P を同じ縮尺・同じ位置で並べる。
- 経過（T）では、課題ごとに10球テストの「◯/10」を日ごとに並べ、8 の線を引く。条件（向き・番手）が違う日は同じ線でつながない。**合格数の合計は描かない**（日によって見られる項目の数＝分母が違う）。

### 8.6 前と後の写真を失わない

- 端末の JPEG は消えることがある（iOS の7日ルール・容量）。サーバーに代表スイングの P1〜P7 と10球テストの課題の P のサムネイル（長辺 360px）・姿勢の時系列（gzip）・タップ・判定を残すので、JPEG が消えても比較はできる（1スイング約 0.05〜0.15MB の見込み・未確認）。
- 消えたら「写真はこの端末から消えました（ホーム画面に追加すると消えにくくなります）。小さな写真はサーバーに残っています」。

### 11.1 色

- **ブランドの色は深い青。** 緑は「範囲の中」の意味の色として取っておく。
- 意味の色は4つ（範囲の中・範囲の外・まずここ・中立）。**色だけで意味を伝えない**（形の印と言葉を必ず付ける）。
- 赤は「範囲の外」ではなく**まずここ**の1つだけ。ほかの範囲の外は注意の色（赤を並べても何から直すかは伝わらない）。

```css

@media (prefers-reduced-motion:reduce){*{animation-duration:.01ms!important;transition-duration:.01ms!important;scroll-behavior:auto!important}}
```

- 動かすのは4つだけ: 押した・選んだの反応、シートの出入り、P のコマの切り替え（横に 16px）、10球テストに合格したときの ✓（1回だけ）。飾りのループと数字のカウントアップはしない。
- スロー再生・P へのジャンプ・［交互］は利用者の操作なので残す（reduced-motion では［交互］を自動で切り替えない）。

### 11.6 図

- 系列の固定: 今回＝`--brand` の実線・塗りの点／前回＝`--neutral` の点線 `2 3`・中抜きの点／ガイドの範囲＝`--good-weak` の面＋端に `--good` の細い破線。緑を「理想の線」に使わない（範囲の帯としてだけ使い、判定の ✓ と意味を重ねない）。
- 凡例は図の上に1行、線の見本つき。目盛りの数字は「なぜ？」を開いたときだけ。確率や信頼区間のふりをした帯を描かない。
- `<title>` と `<desc>`（desc は定型文と同じ文）。色は CSS 変数から（`fill="#` の直書き禁止は既存の検査）。

### 11.7 映像の上の線

- 線は黒 2px の縁＋色 3px（`paint-order:stroke`）。黒の縁に対する比: 白 21:1・`--ov-range` 12.18:1・`--ov-gap` 14.54:1。縁が無いと白地の上で 1.4〜1.7:1、芝（`#6B8E4E` 相当）の上の緑で 2.17:1 しかないので**縁を省かない**。
- 範囲の帯は半透明の面＋黒の縁つきの破線。芝の上で見分けにくければ白の破線に切り替えられるようにする（実機で確かめる）。
- 線の太さはコマの短辺の 0.6%＋1px、関節の点は 8px。
- 注釈の一覧（`web/figures.js`・座標は全部姿勢の点・マスク・本人のタップから計算。Claude は座標を作らない）:

  | id | 描くもの | 見せること |
  |---|---|---|
  | `V-zone` | 範囲（扇＝角度、帯＝位置） | どこに入れば範囲の中か |
  | `V-fixed` | 範囲に入れた線（§7.2） | 理想との差 |
  | `V-club` | タップしたグリップエンドとヘッドを結ぶ線 | シャフトの向き |
  | `V-sway_lines` | P1 の胸・両腰の垂直線（正面） | 横の動き |
  | `V-spine` / `V-head_circle` | P1 の線と頭の円（破線） | 起き上がり・頭の動き |
  | `V-hand_path` | 全コマの手の線（上げと下ろしを色と線の種類で分ける） | 手の通り道 |
  | `V-ball` / `V-target_line` | ボールと棒 | ボール位置・目標線 |
  | `V-ref_skeleton` | 参照動画の骨格 | 比べる相手 |

- カメラの合わせ方を満たしていないコマでは、角度の項目に帯を描かない（「判断できない（カメラが斜め）」→ 撮り方の案内へ）。

### 11.8 アイコン

インライン SVG（`<symbol>` を1回置き `<use>`）。24×24・線 1.75px・`currentColor`・角は丸める。一式（22個）: `home` `history` `practice` `progress` `settings` `camera` `upload` `video` `check` `alert-triangle` `x` `minus` `chevron-left` `chevron-right` `play` `layers`（重ねる） `tap`（2点タップ） `view-dtl` `view-face`（向き） `ten-ball`（10球テスト） `info` `power`（飛ぶ力）。アイコンだけのボタンには `aria-label`。人の形の図は自前の線画 SVG。

### 11.9 権威性・信頼性の具体策

1. どの判定も根拠まで辿れる（元のコマ・線・範囲・出典のページ・札）。
2. 分からないことは理由つきで分からないと出す。見た目の判定に数字を付けない。
3. 同じ条件で比べる（撮影の条件の行）。
4. 色を抑える（青は主ボタンと選択中、赤は「まずここ」1つ）。
5. 分母と前回を添える（「10回中 8（前回 5）」）。
6. 版を出す（アプリ・カタログ・ガイドの版・最終更新日）。要確認の項目は「基準を確かめ中」。
7. 数えて固定する（§16）。

### 13.2 表（`store.go` の schema に足すだけ。`{s}`・`{{ID}}`・時刻は TEXT の既存の流儀）

```sql
-- swings / swing_frames / swing_features はまだ表が無い。既存 §10.3 の形で作り、作るときに次を変える・足す
--   swings: view は §10.3 の CHECK (view IN ('dtl','face_on')) を CHECK (view IN ('dtl','fo')) にする
--           （カタログの view と同じ綴り。変換の層を作らない）。姿勢の時系列は §10.3 の series_gz、
--           fps は §10.3 の fps_measured をそのまま使う（別名を作らない）。足す列:
--           club_class TEXT NOT NULL, cp_catalog_version TEXT NOT NULL DEFAULT '', is_focus_test INTEGER NOT NULL DEFAULT 0, deleted_at TEXT
--           swings.taps_json（§10.3）はボールの2点タップ（スイングに1つ）に使う
--   swing_frames: checkpoint TEXT（'P1'〜'P10'・'P5_5'・'P6_5'。種類は Go で検査し、表の CHECK で縛らない
--                 ＝移行の仕組みが無いので、あとで P を足せなくなるのを避ける）,
--                 taps_json TEXT NOT NULL DEFAULT '{}', thumb {{BLOB}}
CREATE TABLE IF NOT EXISTS {s}swing_checks (
  swing_id INTEGER NOT NULL REFERENCES {s}swings(id),
  item_id TEXT NOT NULL, catalog_version TEXT NOT NULL,
  state TEXT NOT NULL CHECK (state IN ('in_range','out_range','unknown','reference')),
  fault_id TEXT, basis TEXT NOT NULL, reason TEXT NOT NULL DEFAULT '',
  evidence_json TEXT NOT NULL DEFAULT '{}',
  llm_job_id INTEGER REFERENCES {s}llm_jobs(id), created_at TEXT NOT NULL,
  PRIMARY KEY (swing_id, item_id, catalog_version));
CREATE TABLE IF NOT EXISTS {s}focus_tests (
  id {{ID}}, player_id INTEGER NOT NULL REFERENCES {s}players(id),
  plan_id INTEGER REFERENCES {s}plans(id), session_id INTEGER REFERENCES {s}sessions(id),
  item_id TEXT NOT NULL, catalog_version TEXT NOT NULL, block TEXT NOT NULL DEFAULT 'test', -- 'test'(⑥) | 'baseline'(①)
  swing_ids_json TEXT NOT NULL, self_rating_json TEXT NOT NULL DEFAULT '[]',
  in_range INTEGER NOT NULL, judged INTEGER NOT NULL, passed INTEGER,   -- judged < 8 なら NULL
  created_at TEXT NOT NULL);
CREATE TABLE IF NOT EXISTS {s}checkups (
  id {{ID}}, player_id INTEGER NOT NULL REFERENCES {s}players(id),
  baseline_session_id INTEGER NOT NULL REFERENCES {s}sessions(id),
  recheck_session_id  INTEGER NOT NULL REFERENCES {s}sessions(id),
  plan_id INTEGER REFERENCES {s}plans(id),
  scope_json TEXT NOT NULL, items_json TEXT NOT NULL,   -- 作った時点で固定
  result_json TEXT, result_key TEXT, created_at TEXT NOT NULL);
```

- **`plans` に列を足さない。** `store.go` には移行（ALTER）の仕組みが無く、SQLite には `ADD COLUMN IF NOT EXISTS` も無い（§10.3 が「新しい表を足すだけ」にした理由）。代わりに表を1つ足す:

  ```sql
  CREATE TABLE IF NOT EXISTS {s}motion_plans (
    plan_id INTEGER PRIMARY KEY REFERENCES {s}plans(id),
    cp_item_id TEXT NOT NULL, cp_catalog_version TEXT NOT NULL,
    view TEXT NOT NULL, checkpoint TEXT NOT NULL,        -- 10球テストで取り出す向きと P（作った時点で固定）
    created_at TEXT NOT NULL);
  ```

  この表に行があるプランが「動きのプラン」（`kind` は Go が行の有無から返す）。`plans` の NOT NULL の列の埋め方は §8.3。
- **既存 §10.3 からの変更**: §10.3 は「動画の review の結果は `llm_jobs` に入れる（表を増やさない）」だった。項目ごとの状態を日をまたいで引く（比較・10球テスト・推移）ので `swing_checks` を足す。`llm_jobs` には Claude の生の答えと検証だけを残す。`llm_jobs.kind` に `cp_review` を足す。
- 名前: `plans.catalog_version`（ドリル集の版）と紛れないよう、チェックポイントの版は `cp_catalog_version` / `catalog_version`（`swing_checks` の中だけ）と呼ぶ。
- 画像の受け口は §10.3 の「1枚 1.5MB・12枚まで」を「32枚まで」に変える（既定の2スイング × P1〜P7＋中間＋拡大で最大28枚）。
- 画像の上限（`golf` スキーマ全体で初期値 50MB）・使用量の `/healthz` への表示・顔のぼかし・消す操作は既存 §9.9 のまま。

## 20. やらないこと（と理由）

| やらないこと | 理由 |
|---|---|
| 動画をサーバーに送る・保存する | Render 無料（CPU 0.1・512MB）で回らない。プライバシー |
| プロの写真・他人の動画・ガイドの図と文章をリポジトリやアプリに入れる | 権利（R7・R8） |
| 全身の「理想の骨格」・生成画像の「理想のあなた」 | ガイドは範囲を決めているだけ。成り立たない姿勢をもっともらしく描ける |
| Claude に角度・座標を読ませる | 較正されていない数字を「測った」に見せる（R6） |
| 総合点・点数・確率 | ガイドの判定は範囲の中か外か。偽の確信（R4） |
| 「ずれ小」など独自の中間の段 | ガイドに無い基準を作ることになる |
| テンポの合否 | ガイドの目安は1点で範囲が無い |
| 回転量・キネマティックシーケンス・体重配分・地面反力を「測れた」と言う | 1台の 2D では原理的に測れない（項目としては持ち、判断できないと言う） |
| 動きから球筋を言い切る・「これで何ヤード伸びる」 | ガイド自身が「可能性」と書いている（R3） |
| ボール初速・ミート率を前提にした画面 | いまの取り込みに無い（取り込めた日だけ行を足す） |
| 1回の練習で複数の課題 | ガイドの「1回に1〜2項目」。画面は1つだけ |
| 参照動画で数字を比べる | 体格もカメラも違う（そのため特徴量を JS に二重に持たない） |
| 2台のカメラの同期 | 手間に見合わない。同じ1球を両方から見ることはできないと書く |
| 自動のクラブ検出（段1〜4） | 精度を確かめられない。タップをためて較正のラベルにする（段5で検討） |
| タブに「撮る」を置く | HIG: タブは場所の行き来 |
| すりガラス・飾りのアニメーション | 安い端末で重い・動きを減らす設定 |
| `alert` / `confirm` | 画面の中のシートと知らせにする |
