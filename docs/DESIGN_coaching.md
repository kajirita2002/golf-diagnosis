# 設計：解説・理想・アクションプラン・動画（コーチング）

`docs/DESIGN.md` の下に置く設計。DESIGN.md の約束（因果の階層・確率のふりをしない・実験のループが本体・LLM は数字を作らない）は**そのまま守る**。この文書はその上で「読んで分かる解説」「理想」「次に何をやるか」「動画」を足す。

- 4つの設計案（解説レポート・動画・理想・アクションプラン）と、それぞれへの反証のレビューを1本にまとめたもの。案どうしで食い違っていたところは §2.2 で1か所に寄せ、どちらを採ったかと理由を書いた。
- **数字の出どころ。** 例に出す数字は、`testdata/real/2026-09-17/*.tsv`（本人の57球）を `scripts/e2e.py` の `seed_real` で本物の Go API と分析サービスに取り込み、`/shots` と `/analysis` の出力から計算したもの。手で作った数字は無い。区間など実装で少し変わる値は「こちらの計算」と書き、**テストでは実装した関数の出力を固定する**（手で写した値と突き合わせない）。
- **球の番号は `#seq`**（セッション通しの打った順）。画面の「1球ずつ」と実験のブロックがこの番号を使うので、クラブの中の番号（「9番の2球目」）は使わない。
- 閾値はすべて**初期値・要較正**。較正したら版（`analysis/` `physics/` `report/` `plan/` `video/`）を上げる。

## 3. 約束（この文書の全部に効く）

- **R1 事実の文はコードが書く。** 数字・向き（右／左・インサイド／アウトサイド・プッシュ／プル・スライス／フック…）・量（全部・ほとんど・半分・何倍）・因果（〜なので・原因）・比較を含む文は、`claims.py` の定型文にだけ現れる。Claude の文にこれらが出たら捨てる（§5.8）。数字を禁じるだけでは、数字の無い捏造（右と左の取り違え・「ほとんど」）が通るため。
- **R2 数字には範囲を付ける。** 「どのクラブ（まとめ）・何球・測れた球だけか」を必ず添える。範囲の無い値は定型文に差し込めない作りにする。群の値を番手の名前で書かない（7番は2球しか無いのに、アイアン全体の数字を「7番で」と書きかけた）。
- **R3 階層を越えない。**
  - TrackMan だけのときに言えるのは「クラブがインパクトでこうだった（L1）」まで。「スイング中にフェースが開いた」は途中を測っていないので言わない。
  - L2/L3（クラブの動き・体の動き）は動画があって初めて言う。それも「候補」で、L1 とのつながりは実験か統計で確かめるまで言い切らない。
  - 例外は2つだけ。⑦の**ドリルの手順**（体の言葉を含んでよい。L1 を動かせるかを実験で確かめる手段だから）と、⑧の**「動画で見る候補」**（人が書いた定型文）。
- **R4 確率のふりをしない。** 割合より件数を先に書く（「26球中12球」）。区間は「今日の球では〜に偏っていた」とだけ言い、「偶然ではない」とは言わない（球どうしが独立でないと区間は狭く出る）。説明の割合は**単回帰の R²** だけを使う（今の「ばらつきの98%はフェース」は、回帰の share を分散の割合と読み違えている）。
- **R5 言えないことは言えないと書く。** レポートの⑧は空にしない。測っていない項目は、入れ方（手入力・タイルの追加）と一緒に書く。
- **R6 ミスヒットの候補は、回帰と同じ規則で集計から外し、外した数を必ず書く。** 今は回帰（`_drivers`）だけが候補を除き、平均と SD は除いていない。4番UT はトップ1球（#30）を入れるかどうかで「フェースが右を向く偏り」の結論が逆になる。例外は球筋の頻度（`tendency`）とミスの内訳（`miss_budget`）で、起きた球なので候補も数え、候補の数を別に書く。
- **R7 欠けは偶然ではない。** 一番悪い球ほど値が欠ける（アイアンの極端なヒール5球のうち4球はフェースが無い。5番ウッドは打点が欠けた8球の左右のずれの平均 29.6m、取れた15球は 22.2m）。欠けた球を黙って落とさない。欠け方が症状と結びついている指標（ヒールの球でのフェース）は、その症状の実験の目的の指標にしない。
- **R8 TrackMan の中の式を疑う。** 打ち出し方向を「フェース×重み＋パス×残り」で予測した差の SD（Go の `launch_direction_residual` の標本 SD・候補を除く）が、アイアン 0.30°（19球）・ユーティリティ 0.14°（7球）・5番ウッド 0.13°（18球）と小さすぎる（重みを当て直すとさらに 0.23° / 0.10° / 0.12°）。TrackMan がフェースの値を打ち出しとパスから計算しているのかもしれない（**未確認**）。そうなら「フェースで左右の97%を説明」は TrackMan の中の式との一致であって、現実との一致ではない。だから画面では「確かめた」「精度」と言わず、**答え合わせは L0 の実測**（実際に帯へ落ちた球が増えたか）でする。
- **R9 左打ち。** 保存は右打ちの座標（DESIGN §4）。定型文とドリルの向きの語は差し込み（`{dir:right}` / `{lead}` 目標側 / `{trail}` 後ろ側）で持ち、画面が `player.handedness` を見て入れる。打点のトゥ／ヒールは反転しない。
- **R10 Claude が無くても完結する。** つなぎの文が無くても、定型文だけで全部の節が読める。

## 5. 共有部品

### 5.1 `profile`（範囲ごとの集計）と `cross_club`

`analysis/golf_analysis/profile.py`。`analyze_session` の各範囲（まとめ・1本）に `profile` を、セッションに `cross_club` を足す。`/analysis` の形は足すだけにして壊さない。`ENGINE_VERSION = "analysis/0.3"`。findings には `id = "{scope}:{club}:{kind}[:{detail}]"` を付ける（定型文が根拠を指すため）。

| 項目 | 中身 | 規則 |

- **bootstrap はベクトル化する**（`rng.choice(v, (BOOTSTRAP_N, n)).mean(1)`。`stats.bootstrap_mean_ci`）。今の5000回のループを指標×範囲の数だけ回すと、CPU 0.1 で十数秒になりうる。1範囲あたり数十ms を目標にする。乱数の引き方が変わるので版を上げ、テストは関数の出力で固定し直す。
- **`cross_club`**: 比べる単位は種類ごとに1つ（まとめがあればまとめ）で、候補を除いて5球以上。見るのはフェース・パス・打点の `bias` と平均の符号。
  - `common`: 同じ向きの `bias` が2つ以上の単位にある（実データ: 打点のヒールがアイアン〈−20.3mm〉・4番UT〈−7.0mm。候補を除いた7球〉、フェースの右向きがアイアン・4番UT〈候補を除いて〉）。
  - `same_direction_unclear`: 平均の向きは同じだが区間が0をまたぐ（「同じ向きだが、球数が足りず言い切れない」）。実データ: 5番ウッドの打点（平均ヒール 7.6mm・区間 −16.1〜+0.6mm）。

  - `different_type`: 逆向きの `bias`、または別の指標にだけ `bias`（実データ: 5番ウッドのパスの右向き）。
  - **「〜だけ」とは言わない。** 「ほかでは区間が0をまたぐ」は、無いことの証拠ではない。
  - **`different_type` は、その指標を測れた単位が2つ以上あるときだけ作る**（範囲が1つしか無いダミーで「型が違います（ほかの範囲には出ていません）」と書いていた）。文は「ほかの範囲では、この向きの偏りははっきりとは出ていません」とし、「無い」とは書かない。
  - 除いた候補の数は、指標ごとの数ではなく**範囲の候補の総数**で書き、指標を測れた球数を別に書く（「ミスヒットの候補 4球を除き、パスを測れた18球で…」。指標ごとに数えると、同じ5番ウッドで 3球・4球・1球と食い違って見えた）。
- **一番多い枠が同数なら言い切らない。** 並びの順で1つを選ぶと、右打ちと左打ちで①の結論が入れ替わる（5番ウッド: まっすぐ出て左に曲がる 6球と、左に出て左に曲がる 6球）。2つが同数なら「1つに決まりません。◯と◯が同じ数（6球ずつ）」と書き、3つ以上なら①に一番多い枠を出さない。`representative`（典型の1球）もこのときは決めない（F4 も出ない）。

### 5.2 帯と窓（`l1_in_band`）

**「インパクトの数字だけから計算した左右が、目標帯に入る組み合わせだったか」**を1球ずつ見る。理想（§7）・次の目標（§8）・図 F1/F3/F4 がこれを使う。

```
side_L1   = carry·sin(予測の打ち出し) + k·carry·sin(予測のスピン軸)
  予測の打ち出し = Go decomposition.predicted_launch_direction（既存）
  予測のスピン軸 = Go decomposition.predicted_axis_from_face_to_path（既存）
  k             = 種類ごとに、実測の打ち出し・スピン軸・左右から最小二乗で当てる係数（Python）
l1_in_band = |side_L1| ≤ max(side_min_m, side_pct·carry)      … GOOD_TARGETS（既存・Python）
```

- **数えない球:** `thin`・フェースが無い球・極端な打点（打点の段で数える。#18 のようにフェースが取れていても入れない）。
- **閾値を「フェース・トゥ・パスの差」にしない理由:** 帯に落ちるかは打ち出し（ほぼフェース）と曲がり（フェース・トゥ・パス）の両方で決まる。実データでは \|FTP\| ≤ 2.9° のアイアン10球のうち3球が、フェースそのものが右を向いていて右に 8〜14m 外れた。逆に FTP −2.9° でも帯に落ちた球がある。
- **k の当て方:** 候補を除き、打ち出し・スピン軸・左右・キャリーが揃った球で `side − carry·sin(打ち出し) = k·carry·sin(スピン軸)` を原点を通る最小二乗で当てる（実測の打ち出しとスピン軸を使う。予測値ではない）。
- **式が使えるかの判定:** 「予測だけで出した左右の残差 SD」（予測の打ち出しとスピン軸が両方出せた球・候補を除く）が帯の半幅の1/2を超える種類では `l1_in_band` を使わない。アイアン 2.1m（k 0.314 は23球で当て、残差は19球）は使える。**5番ウッドは 12.7m（18球）で使わない**（帯の半幅は約 11m）。
- **10球に満たない種類は「まとめた k」を使い、そう書く。** まとめた k ＝ 同じセッションで**式が使えると判定された種類の球を全部合わせて**当てた k（使えない種類は入れない）。実データの4番UT（7球）は、アイアンと合わせた30球の k 0.375 を使い、残差 1.7m で使える（4番UT だけの k 0.487 なら 2.6m）。**判定を先に出すために、種類ごとの k で残差を見てからまとめる**（順番: 種類ごとに k と残差 → 使える種類でまとめた k → 10球未満の種類の帯の判定）。
- **帯の形（図に描く多角形）は Go:** `physics.Band(carry, spinLoft, lim, k, category, paths) []FaceRange`。パスの値ごとに、帯に入るフェースの下限・上限・中央と、中央での予測の打ち出しとスピン軸を返す。`lim` と `k` は分析サービスから受け取る（`GOOD_TARGETS` を Go に書き写さない）。`EngineVersion = "physics/0.3"`。
- アイアン（キャリー中央値 118.9m・スピンロフト中央値 24.3°・帯 ±5.9m）の帯は、およそ**フェース ≈ 0.31×パス ± 2.0°**。**「フェース＝パス」の対角線ではない**（パスが右なら、フェースも少し右でよい）。キャリーが 100m を超える範囲では帯の幅がキャリーに比例する（`side_pct` が `side_min_m` より効く）ので、窓の角度はキャリーにほとんどよらない。
- **窓**は、帯をパスの中央値で切った断面。アイアンでパスの中央値 +0.4° のとき、およそ **−1.9°〜+2.1°**（非線形の式で −1.86°〜+2.11°）。図はまとめの中央値で描き、判定は1球ずつそれぞれのキャリーとスピンロフトで行う。図の下に「番手ごとの帯は少しずつ違います」と書く。
- **`launch_residual_sd`**（Go の `launch_direction_residual` の標本 SD。候補を除く）を `profile` に出す。0.5° 未満なら、所見に「フェースの値は計測器の計算かもしれません」を info で出す（R8）。
- 窓は線形の見積もりで、今日の球の範囲の外（フェース ±10° など）では当てにならない。窓の中だけで使う。

### 5.3 ミスの内訳（`miss_budget`）

- 1球ぶんの「はみ出し」は `max(0, |side| − Good の幅)`（m）。
- 原因は上から順に割り当てる: 極端な打点かつフェースが取れていて \|FTP\| ≥ 2×MMD → `extreme_and_face`／極端な打点 → `extreme_only`／`thin`／`curve_cause`（`face_to_path` など）／それ以外 → `unknown`。
- フェース・トゥ・パスに割り当てた球のうち、打点が無い球は `no_strike` として別に数える（ネック寄りだった可能性が残る）。
- **球数は、はみ出しが0より大きい球だけを数える**（はみ出し0の球は原因の枠に入れても距離に効かないので、件数だけ膨らむ）。アイアンでは、曲がりの原因がフェース・トゥ・パスの球は12球あるが、はみ出したのは10球（打点なしは4球中3球）。定型文・F6 の件数は全部この数え方にする。
- 定型文は打点のぶんを「`extreme_only` 〜 `extreme_only + extreme_and_face`」の**幅**で言う（数える順で 39%〜51% と変わるので、1つの数にしない）。
- 合計は全部の球のはみ出しの和と一致する（テストで固定）。

### 5.4 issue とゲート（何が先か）

`analysis/golf_analysis/plan.py` の `candidates()`。⑦「次にやること」とプランの両方がこれを使う。

**issue（原因の語彙）**は Go の分解と `profile` から機械的に決める。**打ち出し（フェースの向き）と曲がり（フェース・トゥ・パス）は別々に数える。** フェースの符号で曲がりを割ると、フェース +1°・パス +3° の球（パスに対して閉じているのでドロー回転）を「開き」に入れてしまう。

| issue | 見つけ方（初期値） | 主 KPI |
|---|---|---|
| `strike_heel` / `strike_toe` | 極端な打点が10%以上かつ2球以上、または打点の平均が ∓15mm 以上 | `impact_offset` を `reduce_abs` |
| `strike_scatter` | 打点の SD ≥ 12mm かつ平均の偏りが15mm未満 | `impact_offset` を `reduce_sd` |
| `start_right` / `start_left` | フェースの平均が ±2°以上 かつ \|平均\| ≥ 0.5×SD | `face_angle` を `decrease` / `increase` |
| `start_var` | フェースの SD ≥ 3° で向きの条件に当たらない | `face_angle` を `reduce_sd` |
| `curve_right` / `curve_left` / `curve_var` | フェース・トゥ・パスで同じ規則 | レバーで決める（下） |
| `top_extreme` | `thin` が15%以上かつ2球以上 | 件数だけ（判定しない）。**極端なトップしか拾えない**と書く |
| `low_point` | — | **測れない**（Low Point のタイルが無い）。計測プランで扱う |

- **issue の向きは表の閾値で決める（割り当ての件数では決めない）。** 割り当て（下）は、表で立った issue に球とはみ出しを配るだけ。割り当ては曲がりを打ち出しより先に見るので、件数で向きを決めると、アイアンのように右に出る球の大半が曲がりに取られて `start_*` がほぼ空になる（打ち出しだけに割り当たるのは1球）。曲がりの issue が `curve_var` のときは、右にも左にも曲がった球をそこへ配る。
- **同じレバー・同じ向きの `start_*` と `curve_*`（または `start_*` と `curve_var`）は1つの候補にまとめる。** はみ出しは合計し、主 KPI は `start_*` のもの（`face_angle`）。レバーが違えば別の候補。
- 閾値のすぐ近く（比べる量の差が閾値の10%以内）で決まった向きには、候補に「ぎりぎり」の札を付け、反対側の判定になったときの文も1行出す。
- **レバー:** 曲がりの issue では、ばらついている側を動かす。向きの issue は \|フェースの平均\| ≥ \|パスの平均\| ならフェース、そうでなければパス。ばらつきの issue はフェースの SD がパスの2倍以上ならフェース、逆ならパス、どちらでもなければ `face_to_path` そのもの。**パスそのものは issue にしない**（アウトサイドインもインサイドアウトも、それだけでは直すべきことではない）。
- **平均がずれているときに `reduce_abs` を使わない**（シミュレーションで、平均のずれを `reduce_abs` で拾える割合は `decrease` より低かった）。**例外は打点（`strike_heel` / `strike_toe`）で、`reduce_abs` を使う。** 0 を越えて反対側（トゥ）へ行き過ぎるのも失敗なので、`increase` だと行き過ぎを「改善」と数えてしまう。いまのアイアンの打点は17球すべてがヒール側（−37〜−3mm）なので、行き過ぎない限り \|x\| と −x は同じで、検出力はほぼ落ちない。
- **球の割り当て:** Good でない球を、上から順に最初に当たった原因に割り当てる（`thin` → 極端な打点 → `curve_cause == strike` → 曲がりの符号 → 曲がらずに打ち出しがずれた球は打ち出しの符号 → `unknown`）。両側に同じくらい出ていれば（多い側が少ない側の2倍未満）`*_var` にまとめる。

**ゲート**（先にやる理由が言えるものを先に置く。重みの点数は作らない）:

| ゲート | 条件（初期値） | 止めるもの | 理由 |
|---|---|---|---|
| G0 測れるか | 主 KPI が取れた球が対象の番手で60%未満 | その issue をドリルではなく**計測プラン**にする | 測れない KPI で実験しても `insufficient` にしかならない |
| G1 極端な打点 | 極端な打点が10%以上かつ2球以上（分母はその範囲の全部の球。打点が「-」の球も入れる ―― 測れた球だけを分母にすると、欠けが多いほど割合が上がる） | フェース・パスの issue | その球ではフェースが欠け、フェースの分析から最悪の球が抜ける（R7） |
| G2 打点とフェースが一緒に動く | 両方ある球が10球以上、相関の95%区間（Fisher）が0をまたがない、打点の SD ≥ 12mm | フェースの issue | フェースだけを直した効果を読み分けられない |
| G3 極端なトップ | `thin` が15%以上 | フェース・パスの issue | thin の球では曲がりの原因が出ない |

- ゲートを通ったものは、**割り当てた球のはみ出し（`miss_budget`）の合計**の大きい順 → 球の数 → いちばん易しいドリルの順に並べ、「いま」と「次」の2つまで出す。止めた issue も「◯◯が先。理由: …」と残し、本人が止められたほうを選んでもよい（その場合は「読み分けにくい」と一度だけ確かめる）。
- **打点を先にするのは測りやすさの順で、物理の順ではない**と画面にも書く。
- 実データ: アイアンは「いま」`strike_heel`（G1: 5/26球＝19%。理由は極端なヒールの球が一番大きく外れ、しかもフェースが測れないから。G2 は当たらない: r −0.06）、「次」`start_right`（フェースの平均 +3.3° ≥ 2° かつ ≥ 0.5×SD 2.6°）＋`curve_var`（フェース・トゥ・パスの平均 +2.79° が 0.5×SD 2.85° にわずかに届かず、向きの条件を外れる。**ぎりぎり**の札）。どちらもレバー＝フェース（向き: \|+3.3°\| ≥ \|+0.4°\|、ばらつき: SD 5.2° ≥ 2×1.0°）なので1つの候補「フェース」にまとめ、主 KPI は `face_angle` を `decrease`。5番ウッドは「いま」`strike_scatter`（G2 に**ぎりぎり**当たる。「フェースから始めてもよい」と書き、どちらを選んでももう一方を副 KPI に記録）、「次」`start_var`＋`curve_var`（レバー＝フェース）、`top_extreme`（3/23球・13%）は参考。

### 5.5 定型文（`claims.py`）・用語集・語の一覧

- 主張（claim）は `{id, section, layer, must, qual, facts[], finding_ids[], template}`。`template` は差し込み口（`{v:face.mean}`・`{dir:right}`・`{n:…}`）を持つ文で、値は `profile` からだけ入る。量の言葉（全部・ほとんど・半分）は `qual` として件数から機械的に選ぶ（実装: 差し込み口 `{q:<件数>;<全体>}`／`{qs:…}`（「◯球とも」の形）。合う語が無い件数や、`Claim.qual` と食い違う件数は ClaimError。テンプレートに「全部」「◯球とも」を直書きしない）。
- **用語集**（`glossary.json`）は人が書いて確かめた固定の文（「フェース・トゥ・パス」「クラブパス」「ヒール／ネック」「帯」など）。付録と、画面の用語のタップで出す。
- **語の一覧は `config.py` に1か所**（`LAYER_TERMS`・向きの語・量の語・因果の語・確率の語）。検証（§5.8）・ドリル集の検査（§5.7）・動画の文の検査（§9.6）の全部が同じ一覧を読み、テストで固定する。
  - L3: 体 / 身体 / 腰 / 骨盤 / 肩 / 胸 / 腕 / 肘 / 手首 / 右手 / 左手 / 手のひら / 甲 / 膝 / 頭 / 体重 / 前傾 / 起き上が / 下半身 / 上半身 / 回転 / 開きが早 / グリップ / 握り / 構え / 手元
  - L2: シャフト / 切り返し / トップの位置 / ダウンスイング / テークバック / 寝 / 振り遅れ / 開いて / 閉じて / 返 / こね / すくい
- 画面の言葉は本人の言葉にする（「フェースが右を向いた」「ネック寄り」）。作る側の言葉（「段」「窓」「tail 型」）は画面に出さない。「窓」は「まっすぐ落ちるフェースの範囲」と言う。

描き方の決め:

- **F3** の対角線 `face = path` は「曲がらない」。上側が右へ曲がる、下側が左へ曲がる。**「まっすぐ出る帯」を水平に描かない**（打ち出しは 0.75×フェース＋0.25×パスで決まるので帯は傾く。描くのは `Band` の多角形だけ）。図の下に必ず2行: 「この図にない球: 7（うち極端なヒール 4）」「フェースの向きだけで左右の散りの97%を説明（19球・単回帰）」。帯を使わない種類（5番ウッド）では帯を描かず、理由を1行書く。
- **F4** は角度を3倍に誇張し「模式図・角度は3倍」と書く。飛距離は描かない。
- **F5** は**目標側からフェースを見た形。右打ちはヒール（ネック）が右、トゥが左。** Impact Offset の負（ヒール）を右に描き、図の中に「ネック」「先端」と字で書く。上下は測っていないので点は横1列に積み、「縦の位置に意味はない」と書く。アイアンとウッドでシルエットを変える。中央 ±10mm と ±30mm より外の帯を描く（`physics.CenterStrikeM` / `ExtremeStrikeM`）。
- **F1** は1本ならメートル、まとめなら「左右÷キャリー」と「キャリー÷そのクラブの中央値」。
- **F7** は行が範囲、列がフェース・パス・打点。点が中央値、太い線が IQR、細い線が平均の95%区間。各行の頭に「候補を除いた球数」。
- **スマホ:** `viewBox="0 0 360 H"`（H は 220〜300）、幅100%。文字は12〜13、目盛りは5本まで。点の半径5に、当たり判定の透明な半径12を重ねる。
- **色:** `class="g-good g-miss g-ext g-mishit g-band g-axis"` を付け、`index.html` の CSS 変数で塗る（暗い表示にそのまま追従）。形でも区別する（帯の中 ●・外 ○・極端な打点 ▲・候補 ×）。`fill="#…"` を直書きしない。
- **触れる:** 点は `data-shot="<id>"` を持ち、画面が1か所で受けて「1球ずつ」と同じ面を下から出す。表示は `#seq`。
- **読み上げ:** 各図に `<title>` と `<desc>`（desc は主張の定型文と同じ文）。
- **エスケープ:** クラブ名は利用者の CSV から来る文字列なので、`textContent` で入れる。
- 5球未満の範囲は図を作らない。AI の生成画像は使わない（置き場所が逆の絵が出ても気づけない）。

### 5.8 Claude の呼び方（つなぎの文・動画の質問票で共通）

- 呼び方は `screenshot.py` と同じ（モデルは `screenshot.MODEL` を import、構造化出力 `output_config.format`、`effort`、`betas=["server-side-fallback-2026-07-01"]`・`fallbacks="default"`、`stop_reason` の確認、費用は `Usage.cost_usd`）。**フォールバックで別のモデルが答えることがあるので、`llm_jobs.model` とキャッシュの鍵には応答の `model`（実際に答えたモデル）を入れる**（`MODEL` 定数を入れると、別のモデルの答えを Opus の答えとして使い回し、費用も Opus の単価で数える）。テストは `app._FakeClient` と同じ仕組みの偽物（`NARRATIVE_FAKE_RESPONSE` / `VIDEO_REVIEW_FAKE_RESPONSE`）。
- **ジョブにする。** 生成に数十秒〜1分以上かかりうる。スマホは画面が消えると fetch が切れ、今の Go の `client.post(ctx…)` は要求の ctx をそのまま使うので、**払った生成ごと捨てられる**。Go は `llm_jobs` に行を入れて 202 を返し、要求と切り離した context で Python を呼んで結果を保存する。画面は数秒おきに取りに行く。無料プランは15分で眠り、起き直すとメモリが消えるので、状態は DB に置き、起動時に走っていたはずのジョブは `failed` にする。
- **キャッシュ:** 鍵は `sha256(入力の JSON（小数は表示桁で丸める）+ 版 + PROMPT_VERSION + MODEL)`。球の除外・打点の手入力・Good の上書きで入力が変われば鍵も変わる。同じ鍵なら Claude を呼ばない。
- **上限:** `LLM_DAILY_LIMIT_NARRATIVE`（既定20/日・範囲ごとに数える）・`LLM_DAILY_LIMIT_VIDEO`（既定は上限なし）。拒否・キーが無い・API が落ちている・上限、のどれでも**定型文のまま返す**。
- **つなぎの文（解説・段階A）で Claude が返すのは、節ごとの並びと、つなぎの文だけ。**

```json
{"scope_id": "group:iron",
 "sections": [{"id": "impact", "blocks": [
   {"t": "bridge", "text": "まず、クラブの進む向きとフェースの向きを分けて見ます。"},
   {"t": "claim", "id": "c.path_stable"}, {"t": "claim", "id": "c.face_wide"},
   {"t": "gloss", "id": "g.face_to_path"}, {"t": "claim", "id": "c.sensitivity"}]}]}
```

  - `claim` はコードの定型文を**そのまま**差し込み、`gloss` は用語集を差し込む。Claude の文は `bridge` だけで、事実を持たない。これで差し込み間違い・向きの取り違え・数字の捏造が仕組みの上で起きない（クラブ名も主張の側にあるので、「6番」で数字の誤検出が起きない）。
  - 渡すのは `scope_id`・`label`・`layer_max`・節ごとの主張（id・`must`・読み上げ用の文）・用語集の id。facts の数値は渡さない。主張の文は `<claims>` の中に**データとして**区切る（クラブ名は利用者の文字列なので指示として読ませない）。
  - 検証（全部通らなければ使わない）: ① `scope_id` と節の id・順番が入力と一致 ② `claim` の id が入力にあり、`must` が全部1回ずつ、入力の順番のまま ③ `bridge` に数字（`[0-9０-９]`・漢数字＋助数詞）・向き・量・因果・確率の語・`LAYER_TERMS`・クラブ名・用語集の見出し語が無い ④ `bridge` は80字以内・1節3つまで ⑤ 落ちたら理由を付けて1回だけ直させ、それでも落ちた節は定型文の並びに戻して `fallback_sections` に記録。
  - 段階B（主張の言い換えを許す）は、段階Aを読んでもらって「硬すぎる」と言われたら評価して決める。許すなら、言い換えた文が元の定型文と同じ差し込み口の集合を持ち、量の言葉が `qual` と一致することを検査する。
  - **bridge は許可リストで組む**（2026-09-29 のレビュー。禁止語の一覧では「ひとつ残らず」「十中八九」「北寄りに逸れた」などの言い換えが抜けた）。`narrative.BRIDGE_VOCAB` の語だけで組める文だけを通し、禁止語の検査も重ねて残す。プロンプトにも語の表を渡す（`narrative/0.3`）。
  - フォールバックで別のモデルが答えた範囲は、もう一度押しても呼び直さない（払い直さない）。表示は答えたモデルの名前のまま「別のモデルの答えを表示中」と出し、頼んだモデルの答えとしては出さない。検証に落ちて定型文に戻った範囲はボタンの数に入れず、「検証を通らなかったので定型文のまま」と料金を出す。同じ入力が今日断られた（refusal）ら、その日は呼び直さない。
  - Go の分析サービスへの HTTP の待ち時間（3分）はつなぎの文には使わない（Python は最大 100秒×2 呼ぶので、Go だけが先に切ると払った生成を捨てる）。長さは `LLMConfig.Timeout`（5分）の ctx だけで切る。
- **費用（見積もり・未測定。Opus 5.5 は入力 $4・出力 $20 / 100万トークン。`screenshot.py` の記載と一致）:** つなぎの文は1範囲 約 $0.02〜0.05、1セッション（本体の範囲3〜4つ。§6.1 の規則で、まとめに入る1本ずつと5球未満の範囲はつなぎの文を作らない。実データでは範囲は7つあるが、作るのはアイアン（まとめ）・4番UT・5番ウッドの3つ）約 $0.1〜0.2。動画の質問票（8コマ＋拡大2枚＋シート）は1回 約 $0.11、比較は約 $0.09。実際の `usage` を保存して画面に出し、見積もりを置き換える。

## 7. 理想

**ツアー平均や「正しいスイング」は理想にしない。** 本人の今日の球から作る。画面には上から順に出す。

| 層 | 中身 | 性質 | 置き場 |
|---|---|---|---|
| ① 今日すでに打てている球 | インパクトが帯に入った球と、それが実際にどこへ落ちたか | 実測の球を数えるだけ（ただし下の注意: 式と実測がほぼ同じ数字から来ている可能性がある） | Python（数える） |
| ② まっすぐ落ちる範囲 | 目標帯に落ちるフェースとパスの組み合わせ（帯）と、今のパスでの窓 | 物理の式。前提つき | 形は Go `Band`・閾値は Python |
| ③ 次の目標 | 段の目標（何球まで増やすか・何mm寄せるか）と、L1 の定数から出す目標 | 本人の数から作る | Python（作る）・Go（`plans` に保存） |

### 7.1 ① 今日すでに打てている球

- F1 を「インパクトが帯に入ったか」で塗り分け、下に1行:「インパクトが帯に入った**7球**は、実際に**7球とも**帯に落ちました（左右 SD **3.6m**）。入らなかった**11球**で帯に落ちたのは**1球**でした」。**これが「理想の姿」の絵。** 予測ではなく、今日の自分の球。
- **この「7球とも」を、帯に入れれば落ちることの証拠として書かない。** k は同じ球で当てていて（残差 2.1m）、しかも R8 のとおりフェースが打ち出しとパスから計算された値なら、「インパクトの帯」と「実際に落ちた帯」はほぼ同じ数字を2回見ていることになる（打ち出しの予測と実測の差の SD 0.30°）。言えるのは「今日の球では、式と落ちた場所が合っていた」まで。定型文は「〜に落ちました」（起きたこと）にとどめ、「〜に入れれば落ちます」とは書かない。**帯に入れる練習が効くかの答え合わせは、プランの L0 の答え合わせ（§8.5）でする。**
- 帯を使わない種類（5番ウッド）では出さない。「本人の良い球（帯に入り芯に当たった球）」の件数も出さない（帯を使わないのに「0球」と書かない）。
- 帯に入った球が全部は落ちていないとき（4番UT: 2球中1球）は、「合っていた」の固定の文を出さず、「帯に入った球でも2球中1球しか狙いの幅に落ちていません（計算と実際に落ちた場所がずれています）」と書く。左右のばらつきは3球から出す（2球の SD は出さない）。
- 帯を計算しない理由は「球が足りない」にまとめない（`few_shots` / `no_carry` / `no_flight` / `no_face_path` / `no_category`・`residual_too_large`）。⑥の文と F3 の注記は `band.REASON_TEXT` の同じ表を読み、何を入れれば計算できるかを書く。5番ウッドの文は「狙いの幅 ±11.4m の半分の 5.7m を超えるので、この式は使いません」とし、帯の半幅と式の閾値（その半分）を取り違えない。

### 7.2 ② まっすぐ落ちる範囲

- F3 に帯を描き、窓（今のパスの中央値での断面）を強調する。文:「パスが今のまま（**+0.4°**）なら、フェースが **−1.9°〜+2.1°** のとき、計算の上では左右が狙いの幅に入ります。**パスが右なら、フェースも少し右でかまいません**」（「収めれば入ります」と約束の形にしない。§7.1 の注意）。
- 窓の中央の1球を F4 に点線で重ねる。
- 常に1行:「TrackMan の数字から計算した範囲です。今日の球の範囲の外では当てにならない目安です」（R8）。

### 7.3 ③ 次の目標

- **L1 の定数から出す目標:** 「打点: いまは中央値でヒール **21mm**（17球）→ 目標は芯から **10mm** 以内。ネック寄り（30mm 超）: いまは測れた17球中 **5球** → 目標は0球」。定数（`CenterStrikeM` / `ExtremeStrikeM`）に無い目標は作らない。「今日の中央値まで」のような作った閾値を使わない。

- **直し方の型は数えて決める**（帯の外の球の向きと、帯の中の数から）:

## 8. アクションプラン

### 8.1 流れ

```
候補（§5.4。いま・次）→ 1つ選ぶ（動かせるプランは選手ごとに1つ）
  Plan ＝ issue × ドリル × クラブ1本 × 主 KPI × ブロックの型 × 段の目標（params を固定）
  練習の日ごと: PlanRun ＝ その日のセッションの Experiment（既存）＋ 型
  打つ（画面は圏外でも動く）→ 取り込み → ブロックの割り当て → evaluate（既存）→ 判定と次の手
```

- **クラブ1本。** 既存の評価はクラブ名の完全一致で球を拾う（`strings.EqualFold`）。既定は、群の中で**主 KPI が取れた球が一番多い番手**。アイアンなら9番（10球中8球で打点が取れ、−24.1±11.1mm・極端なヒール3球）。7番は2球なので選ばない。
- **仮説の文は番手の値で書く**:「9番アイアンでヒール側に当たっている（打点の中央値 ◯mm・8球、30mm を超えるヒール3球）。2球並べで打点が真ん中へ寄る」。群の値を使うときは「アイアン全体では」と範囲を書く。
- 仮説は「仮説: 〜すると、〜が減る」の形にし、因果を言い切らない。

### 8.2 見本（アイアン・⑦ 次にやること）

| ステップ | 何をする | 主 KPI と目標 | 組み方 | 次に進む条件 |
|---|---|---|---|---|
| **1** ネック寄りの当たりを減らす | はみ出した距離の **39〜51%** がここから。しかもこの球はフェースが測れないので、先にフェースの実験をすると結果が濁る | 打点 `reduce_abs`（MMD 4mm）。ネック寄りの球数は参考に並べるだけ | 9番で A-B-B-A（各8球。9番の打点の SD 11.1mm から条件ごとに15球）。**打点が「-」の球はシールで見て「1球ずつ」で入れる**（入れないと実質の球数が減り判定できない） | 「効いた」（2回続けて moderate 以上）か、最初の A の打点が芯 10mm 以内 |
| **2** フェースを窓に入れる | 残りのはみ出しの大半がフェース・トゥ・パス | `face_angle` を `decrease`（MMD 1°）。帯に入った球の数を並べて出す（段の目標） | 同じ番手で A-B-B-A | 段の目標の球数を満たし、grade moderate 以上、実際に帯へ落ちた球が減っていない |
| **3** ほかの番手で確かめる | ステップ2で効いた手段が6番でも効くか | ステップ2と同じ | A-B-A | — |

- **今は触らないこと:** パス（もう揃っています。ばらつき **±1.0°**）。
- **試す手段:** ドリル集の `strike.two_balls` ほか（`checked_by` があるものだけ）。空のあいだは「意識する1点を自分で書く」欄だけ。前の実験で同じ KPI が strong / moderate だった介入があれば「前回効いた（日付・判定）」として先頭に、none / worse なら「前回は効かなかった」と添える。
- ステップ2は1回では判定しにくい（§8.3）ので、「2〜3回の練習をまたいで見ます」と先に書く。9番だけで見るとフェースの SD は 7.8°（7球。こちらの計算では 7.80°）で、§8.3 の式では条件ごとに約118球が要る（前の版の「117球」は SD を 7.8 に丸めて計算した値。実装は丸めない値で 118）。1回の型は1ブロック12球（§8.3 の上限）で組み、同じ型を約5回の練習で積む。**組み方の文とばらつきの数字は番手（9番）の値で書く**（群の SD 5.2° で出すと条件ごと53球になり、それを「9番で」と書くと R2 に反する。実装の最初の版がそうなっていた）。9番だけでは平均の区間が0をまたぐ（§6.1）ので、仮説の文も「9番だけでは偏りは言い切れない。アイアン全体では右寄り」と範囲を分けて書く。
- **実装:** 候補の `guards`（`landed_opposite`: 帯の反対側へ外れて落ちた球の数。候補を除いた L0 の実測／`face_median_window`: フェースの中央値と、越えてはいけない窓の端）。文は `{band:lo}`（左打ちは表示の側で `{band:hi}`）を Go の窓で埋める。
- **`decrease` と理想の型のずれを塞ぐ。** §7.3 でアイアンは「真ん中の球は今のままでよい。右へ外れた球を減らす」型なのに、主 KPI の `decrease`（フェースの平均を下げる）は**全体を左へずらしても良く出る**。そこでこの型のときは、「動かさないもの」（§8.5）に**帯の左へ外れた球の数（L0 の実測）**と**フェースの中央値が窓の下限（−1.9°）を下回らないこと**を必ず入れ、どちらかが崩れたら「右の球は減ったが、左へ外れる球が増えました」と出して「効いた」に数えない。

### 8.3 ブロックの型と球数

**標準の型（A-B-B-A）:**

| # | 種類 | 何をするか | 評価 |
|---|---|---|---|
| 0 | `warmup`（5球） | 体を温める | 入れない |
| 1 | `baseline`（A） | いつも通り | A |
| 2 | `drill`（5球） | ドリル（道具あり） | 入れない（「ドリル中」の参考） |
| 3 | `intervention`（B） | 道具を外し、`cue_transfer` だけを意識 | B |
| 4 | `drill`（3球） | 思い出し | 入れない |
| 5 | `intervention`（B） | 同じ | B |
| 6 | `baseline`（A） | 意識を外していつも通り | A |

- **なぜ A-B-B-A か。** シミュレーション（実データの大きさの正規乱数を `experiment._compare` と同じ判定に通した）で、効果ゼロでも、練習の中で打点が直線的に 4mm 良くなっていくだけで、基準 → 介入の順だと moderate 以上が増える。**最初の版の「3割」は条件が書かれておらず再現できなかった。** 条件を固定して計算し直すと（打点 平均 −21mm・SD 11.4mm・MMD 4mm・`reduce_abs`・各400回）、効果ゼロ・変化なしで A 10 → B 10 が 10%、変化ありで A 10 → B 10 が 17%・A 16 → B 16 が 24%、A-B-B-A（各8球）は変化ありでも 10% だった。前後に分けると直線的な変化はほぼ打ち消し合う。**この計算は `scripts/sim_block_order.py` に置き（条件をファイルの頭に書く）、数字を文書に写すときは必ずそこから出す。**最後の A には効果が残って混ざる（効いたぶんが小さく見える）が、控えめな側への偏りなので許し、画面にもそう書く。
- **定着は、次の練習の最初の A** で見る（何もしていない冷えた状態）。DESIGN §3 の練習の中の `retention` は使えるまま残すが、プランの型では使わない。
- **短い版（A-B-A・約30球）:** 準備3 → A 6 → ドリル3 → B 12 → A 6。
- **球数は検出できる大きさから決める。** 条件ごとの合計 n を、今日の SD から `1.96 × SD × √(2/n) ≤ 2 × MMD` を満たす最小の n にし、A・B それぞれ2ブロックに分ける（1ブロック 8〜12球）。主 KPI が欠けやすければ、取れた割合 p で n を割り増す。
  - アイアンの打点（SD 11.4mm・MMD 4mm）なら条件ごとに約16球（8球×2）。10球ずつだと差の区間の半幅は約 ±10mm で、4mm は検出できない。
  - フェース（SD 5.2°・MMD 1°）は約52球が要り、1回の練習では届かない。そのときは「今日のばらつきでは小さな変化は判定できません。大きく動くかを見ます」と書き、練習をまたいで見る。
- **1ブロックの上限は12球**（`BLOCK_N_MAX`）。判定に要る球数がそれを超えても、1回の型は各12球で組み（準備5・ドリル5と3を入れて61球）、「同じ型を約N回の練習で積む（N＝条件ごとの球数 ÷ 24 の切り上げ）」と書く。最初の実装は上限を守らず「各27球・約121球」を出していた。
- **球数を画面で断る。** 標準の型は約45〜55球（上限の12球で組むと61球）で、実データのセッションは全部で57球だった。「1回の実験で約50球使います」と出す。
- 検出力の模擬（シミュレーション）はサーバーでしない（重いうえに結果が揺れる）。式で出す。
- `l1_in_band` の割合を判定の指標（`increase_share`）にするのは後回し（§11 Phase 1b の末尾）。入った・入らないの2値は、16球ずつでも差の区間の半幅が約 ±0.34 あり、MMD 0.2 に届かない（見積もり）。今は並べて出し、段の目標と進む条件に使う。

### 8.4 ブロックの割り当て（練習場の手間を減らす）

- **本線は予定の球数。** 取り込んだあと、そのクラブの球を打った順に並べて型の球数どおりに区切る。画面は**球の帯**（1球＝1マス、ブロックごとに色）で見せ、境目は矢印で1球ずつ動かせる。
- **ボタンは任意の補助。** 押すのはブロックを変えたとき（「次のブロックへ」）と、打ち直したとき（「1つ足す／引く」）だけ。1球ごとには押さない（手袋をしてクラブを持ったまま押すのは続かない）。
- ドリルの球も TrackMan に必ず記録されるので数に入れる。取り込んだ球数と予定の合計が違えば黄色で出す。
- **仮の区切りでは数えない**: 予定の球数で区切っただけ（保存していない）で、しかも打った球の数とも合わない回は、判定の区分は出すが「効いた」「効かなかった」「定着」の回数に入れない（`pending_boundaries`。状態は「区切りを確かめる」）。A の球が準備に入るなどのずれを判定に混ぜないため。人が区切りを保存すれば数える。予定と打った数が合っていれば、画面は記録した時点でその区切りを保存する。
- **練習にできないセッション**: きっかけの診断のセッションと、プランを作る前の日付でもう球が入っているセッションは run にしない（400）。その球に「準備」「ドリル」が付いて診断から消え、解説と候補が変わり、日付順で練習の1回目（物差しの候補）にも入ってしまうため。日付は時差のぶん1日の余裕を見る。
- 区切りを直したら、その run とそれより後の run の保存した評価を捨てる（後の run はその評価を物差し・前の回として読む）。球数とブロックは1トランザクションで差し替える。run の `{blocks: []}` は 400（予定の球数に戻すなら `counts`）。
- ドリルの球だけ TrackMan で別のクラブ名にできれば表の上で自動で分かれる（**未確認**）。

### 8.5 評価（既存の `evaluate` に足すもの）

| 見るもの | やり方 |
|---|---|
| 主 KPI | B と A を比べる。既存の `_compare` のまま |
| 取れた割合 | A と B で、主 KPI が取れた球の割合を並べる。B で大きく下がったら「測れた球だけ良くなっている可能性」と出す（R7） |
| ドリル中（参考） | `drill` と A を同じ `_compare` で比べ、「参考」の札を付ける。判定には使わず、次の手を選ぶのに使う |
| ガードレール | ヘッドスピード・キャリーを `_compare` にかける。「崩れた」は「効いた」と同じ形で数える（向きを逆にした比較が moderate 以上、かつ落ちた量が MMD 以上）。測れなければ「確かめられない」として「効いた」に数えない。崩れたら「当てにいって、振りが弱くなっています」（ヘッドスピード）／「飛ぶ距離が落ちています」（キャリー） |
| L0 の答え合わせ | 基準と介入で、**実際に帯へ落ちた球**の数（件数で言う）。L1 が良くなったのに L0 が増えなければ「インパクト以外（打点・計測）が効いています」（R8） |
| 動かさないもの | ステップ2ならパスの変化（`compare._diff` と同じ判定）。変わったら「代わりに別のものが崩れた」 |
| 件数系 | ネック寄りの球数など。判定せず件数だけ |
| 欠けの最悪の場合 | 本番で、A の欠け方から見込むより多く主 KPI が欠けたら、その球を A でいちばん悪かった値に置いて比べ直し、良い判定（かつ MMD 以上）が残るときだけ「効いた」に数える（R7。割合の差 20% の手前でも黙って比べない。欠けがあれば取れた割合は毎回並べる） |
| 意味のある大きさ | 「効いた」に数えるのは改善量が MMD 以上のときだけ（DESIGN §3。moderate には区間だけ0を越えた小さな差も入る） |
| 除外とミスヒット | 本人が除外した球は数えて「除外した◯球は入れていません」と書く（R6）。ミスヒットの候補（薄い当たり・極端に短い・極端な曲がり）は**主 KPI の比較には含め**、含めた数を書く（その悪い球こそ直したいもの。R6 の例外で、tendency / miss_budget と同じ扱い）。L0 と帯の数えは候補を除く |

- **速さ:** `_compare` は1回 0.17〜0.23秒（作業環境の実測）。CPU 0.1 では10倍前後で、4つ回すと7秒ほど（**未確認**）。抜き出しを numpy の2次元の添字でまとめ（乱数の引き方が変わるので版を上げる）、結果は `plan_runs.evaluation_json` に入力の指紋と版と一緒に保存する（鍵は「入力の指紋|分析サービスの engine_version と plan_version」。版は `/healthz` から取り、数分覚える）。球を外したとき・境目を動かしたとき・分析サービスの版が上がったとき（今日の練習を開いたときにも見る）に計算し直す。分析サービスに届かないときは入力の指紋だけで保存を使う。閉じたプランの状態は、閉じた時点の記録として作り直さない。

### 8.6 進捗と判定

- **物差しはプランの1回目の A。** 日ごとに「その日の最初の A」の KPI（球数つき）を点で打ち、B の値は薄く重ねる。週ごとの数字は A とプランの外で打った球だけで数える（意識して打った B やドリルの球を入れると良く出る）。5球未満の週は点を打たない。
- **効果が無くても、1回で moderate 以上が1割前後出る**（シミュレーション: 打点 0.09・フェースの SD 0.125・各200回。こちらの計算し直しでも打点は 0.10〜0.105。`scripts/sim_block_order.py`）。だから「効いた」は**別の日に続けて2回**。割合は利用者に見せない（確率のふりになる）。見せるのは規則だけ。1球ずつの bootstrap は日によるばらつきを含まないので、日をまたぐ判定は回数の規則で守る。

| 状態 | 条件（初期値） | 画面の言葉と次の手 |
|---|---|---|
| 確かめ中 | 作った直後・1回目 | 「次の練習: …」 |
| 効いたかも | 直近が moderate 以上 | 「今日は寄りました。次の練習でもう一度同じ型で確かめます」 |
| **効いた** | 直近2回（別の日）が続けて moderate 以上、ガードレールが2回とも `worse` でない | 「2回続けて寄りました。次は、何もしていない最初の球に残るかを見ます」 |
| **定着した** | 効いたあと、別の日の2回で、最初の A がプラン1回目の A より moderate 以上（`setup` / `compensation` は3回） | `done` → 最新のセッションで候補を計算し直して次へ |
| 移せていない | ドリル中（参考）は2回とも moderate 以上なのに B は効いていない | 「道具があるとできています。道具なしに移す段です」→ ドリルと本番を1球ずつ交互にする型へ |
| 効かなかった | 3回で「効いた」に届かない、または2回 `worse` | 次に易しいドリルへ替える。ドリル中も動いていなければ「このドリルではクラブの動きが変わっていません」 |
| 詰まった | 同じ issue でドリル2つとも効かなかった | 「TrackMan で見える範囲ではここまでです。動画で見る（`video_checks`）か、コーチに見てもらう段階です」。issue を `blocked` にして次へ |
| 止める | ガードレールが2回 `worse` | 「打点は寄ったが、飛距離が落ちています」と出し、続けるか本人に選ばせる |
| 足りない | `insufficient` | 「あと◯球要ります」。次の型の球数を増やす |

- **「効いた」は直近の判定できた2回（別の日）で見る。** 一度付いても、そのあと崩れた回が来れば「確かめ中」に戻し、「前に効いたになりましたが…」と添える（定着の数えは最初に効いた回から）。いちばん新しい回が「区切りを確かめる」なら、それを先に出す。
- 「止める」のあと本人が「続ける」を選んだら、その時点で最後の run の id を `plans.rationale_json.continue_after_run` に書き、崩れはそれより後の回だけ数える（`POST /v1/plans/{id}/continue`）。
- 「移せていない」のボタンは、同じ直し・同じドリル・同じ番手で `variant: "alternate"` のプランを `?replace=1` で作り直す。「足りない」の次の型の球数は評価の `progress.next_counts` を `today` が返し、画面の組み方の初期値にする。
- **最初に見える言葉**（§0）: 1回ぶんの言葉は評価の `plain`（決まった対応）。良い判定でも「効いた」に数えない回は「良く見えましたが、今日は数えません」と理由の言葉を出し、「良くなった」とは言わない。判定の面は状態の見出し（`STATE_TEXT`）と次の手の1行（`next_text`）だけで、進捗の面の文は進捗でしか言えないことにする。どの文も `gist.check_plain` を通す（テストで固定）。「あなたの記録」の良くなった回とドリルの並べ替えも `counts_as_worked` で数える。根拠の文の「差」は大きさ（MMD に届いたか）と確かさ（区間）を分けて言う。

- **あなたの記録:** `plan_runs` をドリルごとに集め、件数と大きさだけで出す（「3回中2回 moderate 以上」）。同じ issue で次のドリルを選ぶとき、記録のあるドリルを先に置く。あとで Personal Model のラベル付きデータになる（DESIGN §3）。

## 9. 動画（Phase 2〜）

### 9.1 位置づけと役割の分け方

| 動画でやる | 動画でやらない |
|---|---|
| 8つの局面の静止画と、そこでの体の位置関係（2D） | インパクトのフェース角・パス・打点を動画から推定する（TrackMan の担当） |

| 症状の L1 の指標で選んだ、本人の球どうしの比較 | 他人の手本との比較・理想の姿を画像で作る |
| 所見を実験の仮説・介入・確かめる指標につなぐ | 体の動きを L1 の「原因」と言い切る |

- **数字を出すのは姿勢推定**（ブラウザで推定、特徴量の計算はサーバーの Python）。
- **目で見て答えるのは Claude の目隠しの質問票**（症状・所見・TrackMan の数字を知らせず、選択肢で答えさせる）。ヒールだと知らされたモデルは、アーリーエクステンションを「見つける」。

- 画面の文は定型文（§5.5）。Claude の自由な文章で解説を書かせない。

### 9.2 撮り方

- **最初は後方（DTL）1方向だけ**（DESIGN §6 の「DTL 1台から」）。Face-on は Phase 3。
- **ブロック（5〜10球）ごとに1本。** 録画を始め、続けて打ち、止める。1本が実験の1ブロックになり、TrackMan の球との対応づけが「ブロックの中の順番」で済む。1球ごとに撮る運用は、毎球スマホまで歩くことになり1人の練習では回らない（1本抜けると順番が全部ずれる）。1球ごとの録画も受け付ける。
- **置き方（右打ち）:** 打つ人の真後ろ、**目標線と平行で手元を通る線の延長上**、3〜4m、アドレスの手元の高さ（約 0.9〜1.1m）、水平、横向き、レンズ1倍（0.5倍の超広角は端が歪む）、三脚（手持ちは不可）。ボールの横にアライメントスティックを目標線と平行に置く（ArUco の代わり。ArUco は Phase 4 で任意）。
- **60fps で言えること・言えないこと:** 6番のクラブスピード平均 36.9 m/s、5番ウッド 43.3 m/s（2026-09-17 の Average の行）で、1コマの間にヘッドが進むのは 60fps で 0.62m / 0.72m、240fps で 0.15m / 0.18m。**インパクト前後のクラブの形は 60fps では「測れていない」**に入れる。体（骨盤・頭・胸）は動きが遅いので 60fps でも写る。**ブレを決めるのはシャッター速度で fps ではない**（屋内は遅くなる）。P5〜P8 の手首はブレしだいで無効にする。
- **照明のちらつき:** 屋内の照明は 100Hz（東日本）/ 120Hz（西日本）で明滅する。高い fps ではコマごとに明るさが変わるので、比べるときはすべて明るさを揃えるか、形の差（正規化相関）で比べる。
- **撮り方が悪いと言えなくなること（自動で「測れていない」にする）:**

| 問題 | 見つけ方 | 言えなくなること |
|---|---|---|
| カメラが目標線から左右に振れている | 棒の延長が画面の中心（主点）から横に外れる（目標線と平行な棒は画面上で斜めに写るのが正しく、垂直にはならない。**判定は消失点で行う**） | 手元の通り道・シャフトの向き |
| 高すぎる・低すぎる | 棒の延長が中心の高さから外れる | 前傾の角度そのもの（変化量は残す） |
| 揺れ | 四隅を参照と正規化相関で比べる | 移動量のすべて |
| 超広角 | 利用者の申告 | 角度のすべて |
| 体・クラブが切れる | アドレスで点が欠ける | 切れた部位の項目 |
| 30fps で届いた | fps の実測 | 自動検出（手で選ぶモードへ）・P5〜P8 |

- **DTL だけでは言えないこと:** 頭と骨盤の目標方向の移動・ボール位置・手元の先行・肩の傾き（Face-on が要る）。この表はサーバーの検証でも使う。
- **撮影ガイドの画面**（新しいタブ「動画」の中）: 上から見た置き方の図・チェックリスト・**試し撮りのチェック**（1本選ぶと上の自動チェックだけを走らせ ○/× で返す。1本目で失敗すると後が全部使えないので最初に1回勧める）・「撮り方が悪いと何が言えないか」（畳む）。

### 9.3 処理をどこでやるか

| 案 | Render の負荷 | 採るか |
|---|---|---|
| A ブラウザでコマを抜くだけ（人が選ぶ） | ほぼ0 | **Phase 2a** |
| B A ＋ ブラウザで姿勢推定（MediaPipe Pose Landmarker・人のマスクつき） | ほぼ0 | **Phase 2b〜** |
| C 動画をサーバーに送って Python で処理 | 大（0.1 コア・512MB で1本に数分、メモリで落ちる恐れ。未確認の概算） | 採らない |
| D 動画を Claude に直接渡す | — | Claude の入力は画像なので結局コマを抜く |

- **動画は保存しないし、サーバーへ送らない。** 送るのは、review のときに選んだコマの JPEG（保存しない）と、姿勢推定の数値の時系列（小さい）だけ。
- **検出と特徴量の規則はサーバーの Python に1か所**（`analysis/golf_analysis/video.py`・`video/0.1`）。ブラウザの担当は「デコード・姿勢推定・輝度と相関の計算」まで。物理を Go の `physics` 1か所に置いたのと同じ考えで、規則を pytest で固定できる。サーバーは numpy だけで足り、MediaPipe も OpenCV も入れない。
- **ブラウザの流れ（`web/video.js`。動画タブを開いたときだけ読む）:**
  1. `<input type=file accept="video/*">` で選ぶ（複数可）。
  2. デコード: 本命は WebCodecs（`VideoDecoder`）＋同梱の mp4 の分解（全コマを時刻つきで正確に取れる）。使えなければ `<video>` ＋ `requestVideoFrameCallback`。1コマずつのシークは iOS で遅く位置も不正確（H.264 はキーフレームから毎回デコードし直す）なので使わない。
  3. 粗い走査（短辺 160px・全コマ）: 画面の動きの量と四隅の相関 → `POST /v1/video/segment` → スイングの区間。
  4. 細かい走査（区間の前後だけ・短辺 360〜480px）: 姿勢推定（人のマスクも）＋ボールのまわりは**全解像度から**切り出して比べる → `POST /v1/video/checkpoints` → 8コマの時刻と理由。
  5. 切り出し: 各コマを全解像度で描き、人の外枠で切り抜いて長辺 1024px の JPEG。拡大は P1 のクラブとボール、P4 の手元。
  6. フィルムストリップで確かめて直す → JPEG は端末の IndexedDB に置く。
- MediaPipe の WASM とモデルは `web/vendor/` に置いて自前で配る（CDN に頼らない。合計 10〜20MB の見込み・**未確認**）。今の静的配信は `http.FileServer` なので、`/vendor/` にだけ `Cache-Control: public, max-age=31536000, immutable` を付けるハンドラを足し、ファイル名に版を入れる。
- **iOS Safari:** 写真アプリから選ぶと書き出し直されることがある（fps・解像度・コーデックが変わる）ので、実測して画面に出す（「240fps で撮ったのに 30fps で届いた」）。WebCodecs と HEVC の可否、GPU での姿勢推定は**未確認**（だめなら `<video>` の方式と CPU の WASM）。処理中は Wake Lock。処理の実測は `capture_json.perf` に残し、遅い端末では lite のモデルと 360px に下げる。

### 9.4 スイングの切り出しとチェックポイント

- **切り出し:** 明るさを揃えた動きの量が、静止区間の中央値を大きく上回る 0.8〜4秒の区間を候補にし、手首の軌跡がスイングの形（上がって下りてまた上がる）でなければ捨てる。ボールが動かなかったものは「素振り」として対応づけから外す。
- **8コマ**（H＝手首、DTL では見えている側。S＝両肩の中点。L＝アドレスでの胴の長さ。速さは L/秒）:

| コマ | 定義 | 検出の規則（初期値） |
|---|---|---|
| P1 アドレス | 構えて止まった最後のコマ | 始動（H がアドレスから 0.08L 離れ、100ms 離れ続けた最初のコマ）の直前の静止区間の最後 |
| P2 | シャフト水平（バック） | 始動のあと H が腰の高さに来た最初のコマ（画面では「P2 の目安」） |
| P4 | 手元が一番高い | なめらかにした H.y が最小 |
| P5 | 左腕水平（ダウン） | H が肩の高さを下向きに通る |
| P6 | シャフト水平（ダウン） | P5 のあと H が腰の高さまで下りた最初 |
| P7 インパクト | ボールに当たった | 下の挟み込み |
| P8 | シャフト水平（フォロー） | P7 のあと H が腰の高さまで上がった最初 |
| P10 フィニッシュ | 振り終わって止まった | P7 のあと H の速さが 0.3L/s 未満が 0.3秒続いた最初 |

  順序（P1 < … < P10）に反したら失敗。バックスイング 0.6〜1.5秒・ダウン 0.2〜0.5秒を外れたら警告。
- **インパクトの挟み込み:** アドレスのコマでボールをタップしてもらい、全解像度でボールの直径の約3倍の ROI を取る。アドレスの ROI を参照に正規化相関で比べ、`t_arrive`（相関が最初に落ちた＝ヘッドが入ってきた）と `t_gone`（落ちたまま戻らなくなった最初＝ボールが無い）で挟む。表示は `t_gone` の1つ前（`method: "ball_roi"`）。ROI が最初に大きく変わるのはヘッドが入ってきたときで、ボールが出ていったときではない。音は取れれば補助（音だけに頼らない。DESIGN §7）。どちらも取れなければ H がアドレスの位置に一番近いコマ（`status: "estimated"`）。
- 返し方は `{name, t, frame, source: auto|manual, method, status: ok|estimated|failed, reason}`。
- **手で選び直す UI:** フィルムストリップ（2行×4）→ タップで全画面のコマ送り（±0.5秒のスライダー・±1コマのボタン・姿勢の点を薄く重ねる）。直したコマは `source: manual` とし自動の時刻も残す（検出器の較正のラベルになる）。**全部を手で選ぶモード**が Phase 2a の既定。

| `dtl.head_drop` | P1→P7 | 鼻の上下の移動（＋＝下がった） |
| `dtl.hand_path_gap` | P2 と P6 | 腰の高さでの手元の水平位置の差（＋＝下ろすときに外） |
| `fo.*`（Phase 3） | — | ボール位置・頭の左右（トップ・インパクト）・骨盤の左右・手元の先行 |

- 「お尻の線」は**お尻の後ろ側の輪郭**で、関節の中心ではない。DTL では左の腰が体に隠れ、推定の点は当てにならないので両腰の中点を使わない。**正しい動きでもインパクトで線に触れるのは `{lead}` 側のお尻**で、`{trail}` 側は回転して離れる（注記に書く）。
- DTL では体の陰になる側の点を角度に使わない。左打ちは反転して右打ちの座標で保存。
- **有効か無効か:** 使う点の visibility 0.6 未満・撮り方のチェックに落ちた・Claude が `pose_fit: off` と答えたコマ・ブレた手首、のどれかで無効にし理由を残す。
- **誤差の予算:** ①処理の誤差（同じ動画を始める位置を変えて3回処理したばらつき）②置き方の誤差（同じスイングを置き方を少し変えた2台で同時に撮った差。1台なら三脚を置き直したときの P1 のずれで代え、「下限の見積り」と表示）。**球ごとの SD が①②を合わせた誤差の2倍を超える特徴量だけ**を診断に使う。満たさないものは「参考（誤差の範囲）」。

**Claude の質問票（第1段・目隠し）** — 画像（8コマ・拡大2枚・骨格を重ねたシート）と、方向・fps・コマの定義・固定の質問票だけを渡す。症状・所見・TrackMan の数字・症状の表は**渡さない**。`effort: "medium"`。

| id | コマ | 質問 | 選択肢（どれも「判断できない」を含む） |
|---|---|---|---|
| `q.p1_ball_on_face` | P1 拡大 | ボールはフェースのどこに合っているか | 中央 / ヒール寄り / トゥ寄り |
| `q.p7_butt_line` | P7 と P1 | お尻の後ろ側はアドレスと比べて | ボール側に出た / 同じ / 後ろに下がった |
| `q.p7_head_height` | P7 と P1 | 頭の高さ | 下がった / 同じ / 上がった |
| `q.p7_hands_out` | P7 と P1 | 手元と体の距離 | 離れた / 同じ / 近づいた |
| `q.p4_lead_wrist` | P4 拡大 | 左手首 | 甲側に折れている / 平ら / 手のひら側 |
| `q.p4_face` | P4 拡大 | 左前腕に対するフェース | 開き / 平行 / 閉じ |
| `q.p6_shaft` | P6 | シャフトと右前腕 | 前腕より上 / 重なる / 下 |
| `q.grip` | P1 拡大 | 左手のナックルの見え方 | 1個以下 / 2個 / 3個以上 |

- 各答えに `visibility`（clear / partial / not_visible）と、目で見た短い根拠 `visual`（数字は書かせない）。60fps の P6 とブレた拡大は「判断できない」を既定にするよう指示する。
- 出力は `{capture, checkpoints[{name, is_phase, pose_fit, note}], answers[], not_assessable[], extra[]}`。**`extra`（自由な気づき）は表示するだけで、症状との結びつけにも統計にも使わない**（多重比較を避ける）。所見の文・直し方・L1 との関係は書かせない。
- **比較**（2つのスイングの同じコマ）も同じ質問票で、画像には「A / B」とだけ書き、**どちらが症状の球かを伏せ、並べる順を毎回ランダムにする**。サーバーが元の順に戻す。

**第2段（サーバー・LLM を使わない）:** 答え・特徴量・対応づけた球の L1・所見を §9.6 の表で結ぶ。ラベルの規則:
- 「**測れた**」＝対応する特徴量が有効で、誤差の予算を満たし、**向きが答えと合っている**。
- 「**見た目**」＝特徴量が無い、または予算を満たしていない（Claude の答えだけ）。
- 「**測れていない**」＝not_visible・「判断できない」・特徴量が無効。
- 答えと特徴量の向きが逆なら両方を出して「食い違い」と書く（どちらかに寄せない）。
- フェース・手首・グリップの答えは、評価がいくら良くても「見た目」より上に出さない。

**検証（落ちたら1回だけ指摘つきで再依頼し、それでも落ちた項目は出さない。件数は「検証を通らなかったので出していません（2件）」と出す）:** スキーマ・質問票にある `q` と選択肢だけ・`visual` / `note` / `extra` に数字が無い・`is_phase: no` のコマの答えは捨てて選び直しを促す・DTL で言えない部位に触れていない。

**評価（正しさと一致率を分けて測る）:** 姿勢推定で測れる質問（お尻の線・頭の高さ・手元の距離）は、予算を満たした特徴量を正解にして向きの一致率を測る。測れない質問（フェース・手首・グリップ）で測れるのは「同じ入力で2回・左右反転で聞いたときの一致率」だけで、**これは正しさではない**と画面にも書く。`llm_jobs` の結果に溜め、`PROMPT_VERSION` ごとに集計する。利用者はコーチではないので、正解ラベルを本人に付けさせない。

### 9.6 TrackMan との対応づけと症状の表

- **同じ球を結ぶ:** 動画1本を TrackMan の球の範囲（`seq_from`〜`seq_to`。実験のブロックと同じ書き方）に当て、素振りを除いたスイングを順番に当てる。本数が合わなければ赤で出して人が直す。一覧にはインパクトのサムネイルと、その球のキャリー・左右・ミスの型・打点を並べる。**人が確かめてから決め、確かめていない対応づけは統計にも比較にも使わない。** 撮影時刻での対応づけは Phase 3（mp4 の creation_time を読めるかは**未確認**）。
- **症状 → 確かめどころの表**（`video_candidates.py` に**データとして**持つ。第2段・統計・画面・§6.3 の「動画で見る候補」が全部これを読む）:

| 症状 | 判定（既存の出力） | 数値（事前登録・3つまで） | 質問票 | 撮り方 |
|---|---|---|---|---|
| S1 ネック寄りの当たり | `extreme_strike` の `contact == "heel_extreme"` が2球以上 | `dtl.butt_line_gap`・`dtl.hands_out`・`dtl.spine_tilt_delta` | `q.p1_ball_on_face`・`q.p7_butt_line`・`q.p7_hands_out` | DTL。**その球の動画**が要る（散発的） |
| S2 打点が全体にヒール寄り | 打点の平均がヒール側に 10mm 超 | 同上 | `q.p1_ball_on_face`・`q.p7_butt_line` | DTL。どのスイングでもよい（系統的） |
| S3 フェースが系統的に右 | フェースの `bias` が right | なし（姿勢推定では見えない） | `q.grip`・`q.p4_lead_wrist`・`q.p4_face` | どのスイングでもよい |
| S4 フェースが散発的に大きく右 | 中央値から MAD の3倍より外の球 | なし | S3 と同じを**その球と普段の球で比べる** | その球の動画 |
| S5 / S6 パスが右 / 左 | パスの平均が ±2° 超 | `dtl.hand_path_gap`・`fo.ball_position`・`fo.pelvis_shift_impact` | `q.p6_shaft` | 入射角を一緒に見る（下に打つほどパスは右に出る） |
| S7 アイアンの入射角が浅い・上向き | 平均が 0° 以上（基準の出典を確かめて定数に入れる） | `fo.*` 3つ | `q.p7_head_height` | Face-on（Phase 3） |

  実データのアイアンでは S1・S2・S3・S4（10.6°/14.3°/15.6° の3球）・S7 が当たる。**S3 と S4 は撮り方が違う**（S3 はどのスイングでも写る。S4 はその球の動画でしか見えない）ので、画面で分けて案内する。
- **比べる相手は症状の L1 の指標で選ぶ**（L0 の Good では選ばない）: S1・S2 は芯（10mm 以内）の球 対 ネック寄りの球、S4 はフェースが外れた球 対 中央値 ±MAD の球。芯の球が「良い形」とは限らない（アイアンの芯寄り3球の1つ #26 は、フェース 14.3° で右へ 31m のプッシュスライス）ので、打点の比較相手として出し、「良い形」とは呼ばない。各群5球に満たないあいだは「例」とだけ表示する。
- **統計（Phase 3）:** 対応づけを確かめた球が10球以上たまったら、表の数値（最大3つ）を**全部**、L1 との相関の bootstrap 95% 区間で出す（0 をまたいだものも隠さない。`stats.py` に相関の関数を新しく足す）。群の比較は `experiment._compare` と同じ出し方。S5・S6 は入射角を一緒に入れた回帰で、入射角を入れても残る関係だけを「候補」にする。
- **実験へ:** 動画の特徴量を副次の指標にするには、`experiment._values` が読む `metrics` に `video.<id>` として入れ（`shot_id` でつなぐ）、`config.MMD` に誤差の予算から決めた値を足す。**介入のブロックで動画の特徴量が動いたのに L1 が動かなければ、その候補は外れ**として記録し表示する。

### 9.9 保存・プライバシー・費用

- **解析用の JPEG は端末（IndexedDB）に置く。** review のときに送り、サーバーは Claude に渡したら捨てる。canvas から作った JPEG には位置情報が入らない。
- **サーバーに残すのは小さなものだけ**（1スイング約 0.05MB の見込み）: 代表のコマのサムネイル（長辺 360px）・姿勢の時系列（gzip）・特徴量・質問票の答え・検証の記録。
- **保存先は english-tts と共用の PostgreSQL（`golf` スキーマ）。** 容量が尽きると english-tts の保存が止まるので、`golf` の画像に上限（初期値 50MB）を設け、超えたら古いサムネイルから消し、使用量を `/healthz` に出す。無料の PostgreSQL の容量と期限は**未確認**（確かめてから上限を決め直す）。
- 顔は既定でぼかさない（本人専用・`APP_PASSWORD`）。「顔をぼかして送る」を選べる。隣の打席の人が写ったら2人目として見つけてぼかす。Claude の API に画像を送ることは最初の1回だけ画面で断る。スイングを丸ごと、または画像だけ消せる。
- **review は人が押したときに、症状の代表のスイングだけ**（1セッション2〜4回・約 $0.3〜0.8 の見込み）。全部の球で回すと57球で $8〜17 になる。姿勢推定・特徴量・対応づけ・統計は全スイングで無料。
- **本物の動画をリポジトリに入れない**（顔が写る）。

- 閾値はすべて初期値（`spread` の 1.5倍・3倍、ゲートの 10% / 15% / 15mm / 12mm / 60%、±2°・0.5×SD・SD の2倍、`extreme_and_face` の 2×MMD、式を使う条件「残差 SD が帯の半幅の1/2」、文の型の 3/4 と 1/4、`IDEAL_SHARE_GOAL` 0.75・幅 0.2、打ち出しの差の 0.5°、動画の 0.08L・0.3L/s・消失点の 5%・MAD の3倍・誤差の2倍）。較正したら版を上げる。

**リスク**
- 解説が長くなって読まれない → ①だけで分かる作りにし、各節は要点1行＋続き。1a の完了条件で本人に確かめる。
- プランが重くて続かない → ボタンは任意、短い版（約30球）を用意、圏外でも動く。
- 共用の PostgreSQL を画像で埋める → 画像は端末に置き、サーバーはサムネイルだけ・上限つき。
- ドリルの向きの誤りで逆の動きを練習させる → 人の確認（`checked_by`）が無いドリルは出さない。図は人が描く。

## 14. やらないこと（と理由）

| やらないこと | 理由 |
|---|---|
| 確信度（%）・「偶然ではない」・効く確率を出す | 較正されていない（DESIGN §2）。件数・区間・判定の言葉と規則で言う |
| 回帰の share を「ばらつきの◯%」として出す | share は R² の落ち幅を配ったもので、分散の割合ではない。単回帰 R² だけを使う |
| Claude に事実の文（数字・向き・量・因果）を書かせる | 数字を禁じても、右左の取り違えや「ほとんど」は数字無しで作れる。コードの定型文だけにする |
| TrackMan だけで体の動きを助言する | 階層を越える。「動画で見る候補」に置く |
| 「もしも（直したらこう落ちる）」の予測の散布を出す | パスもキャリーも動かない・TrackMan の式の上の計算、という仮定の積み重ねで、一番強い絵が偽の確信を与える。理想は今日の実測で見せる |
| 「理想」をツアー平均・プロの写真・生成画像にする | 本人の L1 が直る証拠が無い。著作権・肖像権。成り立たない姿勢を描ける |
| 「理想」を L0 の Good 球で選ぶ | 打ち消し合いの偶然でも Good になる。キャリーの判定が抜けた Good もある |
| 優先に重みを足した点数を使う | 0.1 の差に意味が無いのに順番だけ決まる（偽の精度）。ゲートで理由を言う |
| 検出力のシミュレーションをサーバーで回す | CPU 0.1 で1分以上かかり、結果も揺れる。式で球数を出す |
| 動画をサーバーへ送る・保存する | Render 無料（CPU 0.1・512MB・ディスク無し）で回らない。顔が写る。共用の DB を埋める |
| 1球ごとに1本撮る運用を基本にする | 1人の練習では回らず、1本抜けると対応づけが全部ずれる |
| Claude に症状を知らせてコマを見せる・症状との結びつけを任せる | 見たいものを見る。事前の表を迂回した多重比較になる |
| Claude に体の角度を読ませる・確からしさを自己申告させる | 読めるかを測っていない。自己申告は較正されていない |
| 体の特徴量を全部比べて差が出たものを拾う | 多重比較で必ず何かに差が出る（DESIGN §1） |
| ドリルの本文を Claude に書かせる・言い換えさせる | 置き場所の逆など、誤りに気づけない。DESIGN §7 の「コーチが作った集から選ぶ」 |
| 立てた物を打ち出しの先に置くドリル | 跳ね返りが危険。マットにティーが刺さらない |
| 1球ごとにボタンを押させる | 手袋をしてクラブを持ったままでは続かない。予定の球数と球の帯で割り当てる |
| 診断した日の値を段の物差しにする | 平均への回帰で、何もしなくても良く見える |
| 欠けた球を黙って落として評価する | 一番悪い球ほど欠ける（R7）。取れた割合を並べる |
| `experiments` に列を足す・`targets` 表を別に作る | 移行の仕組みが無く、同じことを2か所に持つことになる。新しい表だけで足りる |
| 図を Python で SVG にする | 帯の形は Go の物理が要るので往復が増える。図の中身だけをサーバーが返す |
